Fresh-input check of one step, before it is committed. You write new scenarios and change nothing else: no source file, no existing scenario, no step, no fixture.

The step: the host starts git, and the client of the forge, with a closed list of environment variables (design and threat table: `docs/design/orchestration-fable-5-2.md` §14, « Un environnement fermé pour git : conception »). The code: `closedEnvironment` in `packages/sandbox/src/tree-fingerprint.ts`, in `tools/test-gate/src/infrastructure/git.ts` and in `tools/deliver/src/infrastructure/host-process.ts`; the key `environment` of `tools/deliver/deliver.json` and its schema (`tools/deliver/src/infrastructure/deliver-schema.ts`); the adapters `git-repository.ts` and `gh-forge.ts`; `tools/deliver/src/main.ts`; `features/support/git-environment.ts`. Its scenarios: `packages/sandbox/features/tree-fingerprint.feature`, `tools/test-gate/features/closed-environment.feature`, `tools/deliver/features/command.feature`, `config.feature`, `host-process.feature`, `features/descriptive/closed-git-environment.feature`.

What to do: think as someone who wants git, on the host, to act on another repository, to read a configuration, to start a program or to print a credential, by what is set in the environment of the process; and as someone who wants the delivery to lose what it needs to identify itself. Invent inputs those scenarios do not use and write them as scenarios, in new files only: `packages/sandbox/features/tree-fingerprint-fresh.feature`, `tools/test-gate/features/closed-environment-fresh.feature`, `tools/deliver/features/environment-fresh.feature`.

Rules:
- At least 20 scenarios in all (a Scenario Outline counts once per Examples row). Each uses an input no existing scenario uses: another variable git obeys (`GIT_WORK_TREE` alone, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_CEILING_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_PARAMETERS`, `GIT_EXEC_PATH`, `GIT_EXTERNAL_DIFF`, `GIT_PAGER`, `GIT_TRACE`, `GIT_TRACE2_EVENT`, `GIT_ATTR_SOURCE`, `GIT_LITERAL_PATHSPECS`, `GIT_OPTIONAL_LOCKS`…), a variable that is not git's and still changes what git or the forge client does (`LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `NODE_OPTIONS`, `SSH_ASKPASS`, `http_proxy`, `HTTPS_PROXY`, `GH_HOST`, `GH_CONFIG_DIR`, `XDG_CONFIG_HOME` when it is in the list, `HOME` pointing elsewhere), a name of the list that is unset, set to the empty string, or set to a value with a line break; for the schema of `environment`: names at the limits of the expression, lower case, a `GIT_` prefix in another case, 0, 1, 32 and 33 names, a name twice in another position.
- Use only step texts that exist in the step files of those features, exactly as written there. If an input you want cannot be expressed with the existing steps, do not write it as a scenario: list it in your report under "left out", with the step it would need.
- The expected result of each scenario comes from the contract: the design section named above and the comments of the source files. Do not derive it from how the code happens to behave. Above each scenario write one comment line, `# expected because: <the sentence of the contract, or of the documentation of git, it follows from>`. Where the contract says nothing, still write the scenario with the result you hold to be right, and start the comment with `# contract silent:`.
- If, reading the code, you believe a scenario you wrote will fail on the host, keep it as the contract wants it and say so in your report: that is a finding, not a reason to change the expectation.
- A scenario you write must be able to fail: say in your report, for each, what leak or what defect would make it fail. A poison that could not change the outcome even when it leaks proves nothing: do not write it.
- You may run `npx cucumber-js --profile replay <your feature file>` in your sandbox to see whether the steps match; a scenario that fails here is not to be changed for that reason.

Report: the list of scenarios with, for each, the class of input, what would make it fail, and whether you expect it to pass on the host; then "left out"; then anything in the design or the code that you hold to be wrong and could not express.

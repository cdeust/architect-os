# packages/sandbox

Ce paquet contient le port `SandboxRunner`, l'adaptateur srt (`@anthropic-ai/sandbox-runtime` 0.0.83), le proxy d'authentification de l'hôte et l'outil de code isolé de la brique 1a.0 ([`docs/design/platform-v3-srt.md`](../../docs/design/platform-v3-srt.md), §6 et §8). Les preuves sont dans [`docs/design/journal.md`](../../docs/design/journal.md), §14 et §15.

Les scénarios Gherkin du paquet sont dans `features/` (étapes dans `features/steps`) : proxy d'authentification, profil, `code.json`, worktree, contrat `SandboxRunner` sur l'adaptateur en mémoire. Ceux qui lancent de vraies sandboxes srt sont dans `features/sandbox/` à la racine du dépôt, sous macOS comme sous Linux ; ils échouent, sans jamais être sautés, quand srt ne peut pas tourner. Le faux srt sans isolation est `fixtures/no-isolation-srt.mjs`.

## Accès au builder

Depuis la racine du worktree cible, l’hôte fournit dans `ARCHITECT_OS_STEP_EVIDENCE` le chemin absolu d’un reçu privé sous `~/.config/architect-os/step-admission/`. Le lanceur vérifie le reçu avant d’ouvrir une session.

```bash
"$LAUNCHER/aos" -- npm --prefix "$LAUNCHER" run step -- "$INTAKE/delivery"
```

L’entrée directe `run code` renvoie `STEP_ADMISSION_REQUIRED` (code 2). Après admission par Step, la session de construction suit cet ordre (`code.json`, `profiles/builder.json`) :

1. Il lit l'identifiant Claude de l'hôte dans le trousseau, comme Claude Code sur l'hôte, et le garde en mémoire dans le proxy d'authentification (`src/auth-proxy.ts`). Le proxy est natif, sur `127.0.0.1:<port aléatoire>`.
2. Il crée sous le temporaire de l’exécution admise un dossier propre à la sandbox, qui contient :
   - le profil srt résolu (en lecture seule) ;
   - `tmp` (`CLAUDE_CODE_TMPDIR`) ;
   - `config` (`CLAUDE_CONFIG_DIR`), avec `settings.json` (`sandbox.enabled: false` et les règles `permissions.deny`, en lecture seule pour la sandbox) et `.claude.json` (onboarding fait, dossier approuvé).
3. Il lance le canari, puis `srt --settings <profil> -- env -u NO_PROXY -u no_proxy claude --bare --settings <config>/settings.json --strict-mcp-config --append-system-prompt-file <lanceur>/packages/sandbox/prompts/build.md <arguments>`. Sous `--bare`, Claude Code ne charge ni hooks, ni plugins, ni skills, ni serveur MCP, ni mémoire automatique, ni CLAUDE.md : chaque entrée est déclarée dans `code.json` ou le profil. Le prompt passé est celui du lanceur, jamais le `CLAUDE.md` du worktree, que la sandbox peut écrire. La session lit les règles du projet par `git show HEAD:CLAUDE.md`, comme des données de moindre autorité, comme Claude Code lui-même livre `CLAUDE.md` en message utilisateur et non dans le prompt système. La sandbox reçoit seulement `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>`, `ANTHROPIC_API_KEY=<jeton de session aléatoire>` (sous `--bare`, la seule authentification lue avec `apiKeyHelper`) et `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, qui retire ce jeton de l'environnement des commandes que Claude Code lance.
4. À la fin, il révoque le jeton de session, ferme le proxy et retire le dossier temporaire.

Aucun secret ne franchit la frontière. Le proxy ne relaie que `POST /v1/messages` et `POST /v1/messages/count_tokens` vers `api.anthropic.com`, avec l'identifiant de l'hôte en `Authorization` ; le jeton de session, lu dans `x-api-key`, ne part jamais vers l'amont. Il répond 403 à toute autre route ou méthode, et 401 sans le jeton de session. Il répond aussi 403 à un corps hors de la politique de `code.json` (`authProxy.policy`, lue par `src/request-policy.ts`) : champ racine non listé, outil typé côté serveur (`web_fetch`…), image ou document dont la source n'est pas dans le corps (URL, fichier), corps au-delà de 64 Mio. Une liste de domaines accorde des capacités : par `api.anthropic.com`, ces champs feraient lire au modèle des données hors de portée de la sandbox. Il écrit une ligne d'`usage` par réponse (modèle, tokens, horodatage, route, type d'erreur, jamais le contenu) dans `${ARCHITECT_OS_RUNTIME_ROOT}/state/usage.jsonl`, créé au démarrage en mode 600 dans un dossier 700 ; un journal qui ne s'écrit plus arrête le proxy, qui répond alors 503 en nommant la cause. Les anciens journaux d’usage et de livraison restent consultables dans `~/.local/state/architect-os/`. Les nouvelles livraisons ajoutent leurs lignes à `${ARCHITECT_OS_RUNTIME_ROOT}/state/deliveries.jsonl`.

Le proxy ne renouvelle pas l'identifiant OAuth. Le jeton de rafraîchissement change à chaque usage : le renouveler ici déconnecterait l'hôte. Quand l'identifiant expire, le proxy relit le trousseau ; s'il a expiré, il répond 503, et il suffit de lancer une session `claude` sur l'hôte.

Le checkout du lanceur (son code, son `node_modules` avec srt) doit être hors du worktree visé, sinon une session pourrait réécrire srt ou le lanceur pour le lancement suivant. Lancé depuis le worktree qui l'héberge, l'outil refuse de démarrer (`ISOLATION_UNAVAILABLE`). Après fusion, le checkout principal `<repo>` sert de lanceur.

Le dossier de configuration est recréé à chaque lancement : aucun historique de session ne passe d'un lancement à l'autre (pas de `--resume`).

## L'étape

Cinq fichiers portent les parties pures d'une étape de l'orchestration (`docs/design/orchestration-fable-5-2.md`), sans lancer de processus. `src/step-file.ts` lit `step.json`, le fichier descriptif d'une étape : modèle, effort et limite en secondes de la session de construction (`build`), puis `scouts` (les éclaireurs, au plus 8, facultatif : absent ou vide, l'étape n'a pas d'éclaireur) `checks` (les contrôles, voir plus bas) et `reviews` (au plus 8, facultatif : absent ou vide, l'étape n'a pas de revue), chacun avec un `name` (`^[a-z][a-z0-9-]*$`, 32 caractères au plus, unique dans l'étape : il entre dans des noms de fichiers), son modèle, son effort et sa limite, et `parallel`, le nombre de sessions d'une même phase (éclaireurs, revues) qui peuvent tourner en même temps (de 1 à 8, 2 s'il est absent) ; un éclaireur, un contrôle et une revue peuvent porter le même nom, deux éclaireurs non, ni deux contrôles ; toute clé inconnue est refusée, dont l'ancien `review` au singulier. `src/measure.ts` mesure une session `claude -p --verbose --output-format stream-json` : réponses, tours, durée, coût, coût par modèle (`costByModel`, le `costUSD` de chaque clé de `modelUsage`, qu'un événement `result` doit porter pour être un résultat), jetons, cache, modèles, refus de permission et rapport ; une session tuée à sa limite, sans événement `result`, reste mesurable. `src/review-verdict.ts` porte le contrat du verdict de revue, dont `prompts/review-verdict.schema.json` est exactement le schéma généré, et `blocks`, qui dit si un verdict bloque. `src/step-checks.ts` porte les parties pures des contrôles : `outputTail`, `passed` et `renderChecks`. `src/scout-facts.ts` porte le contrat des faits d'un éclaireur (`{ facts, open }` : au plus 40 faits `{ file, line, quote, note }`, une citation d'une seule ligne de 300 caractères au plus ; au plus 10 `open`), son schéma pour `--json-schema` (draft-07, généré), `verifyFacts` et `renderFacts`. `verifyFacts(facts, read)` ne touche à aucun fichier : `read` lui donne le texte d'un fichier du worktree, et chaque fait est vérifié ou rejeté avec une raison parmi `chemin refusé` (chemin absolu, segment `..`, barre oblique inverse, NUL, saut de ligne, ou sous `.git/` : `read` n'est pas appelé), `fichier absent`, `ligne absente` et `citation absente de la ligne` (la citation doit être une sous-chaîne de la ligne, telle quelle, sans rogner ni changer la casse) ; un fait identique à un fait déjà vérifié est écarté, non rejeté. `renderFacts` écrit le bloc `## Facts found by scouts` que la construction reçoit : la citation et la note passent par `JSON.stringify`, aucun saut de ligne ni titre ne s'y glisse.

La commande qui les assemble, `src/step-tool.ts` (`src/step.ts` n'est que son point d'entrée), joue une étape de la boucle (§4) :

```bash
"$LAUNCHER/aos" -- npm --prefix "$LAUNCHER" run step -- <dossier>
```

`<dossier>` est un chemin absolu, hors du dépôt, qui contient `step.json`, `brief.md` et, pour chaque éclaireur `<name>` de `step.json`, `scout.<name>.md`, sa question. Avant toute session, un refus (pas de dossier ou plusieurs, chemin relatif, `step.json` absent, pas du JSON ou refusé par `parseStepFile`, `brief.md` absent ou vide, `scout.<name>.md` absent, vide ou fait de blancs) écrit une ligne `architect-os step: <raison>` sur stderr et rend 2. D'abord les éclaireurs (`scout.json`, mêmes arguments que les revues dont `--json-schema` est le schéma des faits, leur question sur stdin, arrêtés à leur `limitSeconds`), au plus `parallel` à la fois, démarrés dans l'ordre du fichier et tous attendus, par le même mécanisme que les revues. Pour chacun, l'hôte lit les fichiers (`readSource`, une dépendance injectée ; la vraie ne rend un texte que si le chemin réel du fichier, liens suivis, est un fichier ordinaire sous le chemin réel du worktree, donc un lien qui en sort est `fichier absent`) et vérifie chaque citation avec `verifyFacts`. Un éclaireur invalide (pas de sortie structurée, ou refusée par le schéma), non terminé ou arrêté à sa limite ne donne aucun fait, et l'étape continue : le brief se suffit. Un éclaireur dont la session lève fait sortir l'étape en 2 après la fin des autres éclaireurs, sans construction. Puis la session de construction, dont le brief est `brief.md` suivi d'une ligne vide et du bloc de `renderFacts` sur les faits vérifiés de chaque éclaireur, dans l'ordre du fichier, s'il y en a au moins un (`code.json`, `-p --verbose --output-format stream-json --model <modèle> --effort <effort>`, le brief sur stdin), arrêtée à `build.limitSeconds` (la sandbox est stoppée, le flux écrit jusque-là est gardé) ; puis, seulement si la construction est terminée et non arrêtée, les contrôles (voir plus bas), puis, si tous ont passé, chaque revue de `step.json` (`review.json`, mêmes arguments plus `--json-schema` du schéma généré par `z.toJSONSchema` en draft-07, le brief de l'étape, suivi du bloc des contrôles s'il y en a, sur stdin), arrêtée à sa `limitSeconds`. Au plus `parallel` revues tournent en même temps ; elles démarrent dans l'ordre du fichier, chacune dès qu'une place se libère. Toutes sont attendues, quoi qu'il arrive aux autres : si une session lève (`ISOLATION_UNAVAILABLE`, …), les autres vont à leur fin, puis l'étape sort en 2 avec la ligne de la première en échec dans l'ordre du fichier. Le stderr des sessions passe tel quel sur celui de la commande.

Dans le parcours Plan, l’opérateur autorise la matérialisation du dossier d’entrée après avoir vu l’aperçu. Pour démarrer les sessions, Step exige aussi une preuve d’admission liée à l’arbre cible, au brief, au lanceur et aux résultats des spécimens. Step lit les entrées au lancement et garde leur contenu pour l’archive. Sous la racine admise, l’hôte réserve `state/steps/<identifiant-run>/<nom>/` pour les résultats et `run/<identifiant-run>/tmp/steps/<nom>/` pour les flux bruts `*.stream.jsonl`. Ces deux dossiers sont privés. Une réservation déjà présente fait refuser la tentative avant toute session, y compris après une interruption. Si la réservation des flux échoue, l’hôte retire le dossier de résultats qu’il vient de créer lorsqu’il est encore vide et possède la même identité sur le disque. L’archive canonique `steps/<nom>/` du worktree est décrite ci-dessous.

Les sorties se répartissent selon cette règle. Pour chaque éclaireur `<name>`, `scout.<name>.stream.jsonl`, `scout.<name>.measure.json` et `scout.<name>.facts.json` (`{ verified, rejected, open }`, chaque fait rejeté avec sa `reason`, ou `{ "invalid": "<pourquoi>" }` quand la session n'a pas abouti, n'a pas donné de sortie structurée ou en a donné une que le schéma refuse) ; `build.brief.md`, le brief donné à la construction (celui de `brief.md` quand aucun fait n'est ajouté ; les revues reçoivent `brief.md` tel quel, ou, avec des contrôles, la consigne et leur bloc : `review.brief.md`, écrit dès que la phase des revues est atteinte) ; pour chaque contrôle joué `<name>`, `check.<name>.json` ; `build.stream.jsonl` (écrit au fil de l'eau), `build.measure.json` (`measureSession` sans `report` ni `structuredOutput`, plus `exitCode` et `stopped`), `build.report.md` ; pour chaque revue `<name>`, `review.<name>.stream.jsonl`, `review.<name>.measure.json` et `review.<name>.verdict.json` (le verdict, ou `{ "invalid": "<pourquoi>" }` sans sortie structurée ou avec un verdict refusé). Les fichiers `review.stream.jsonl`, `review.measure.json` et `review.verdict.json` ne sont plus écrits. Stdout porte une seule ligne JSON : `scouts`, un objet par nom d'éclaireur, dans l'ordre du fichier, chacun `{ model, completed, exitCode, verified, rejected, open, costUsd, costByModel }` (`completed` : la session a abouti sans être arrêtée ; les trois nombres comptent les faits vérifiés, les faits rejetés et les `open`), `{}` sans éclaireur ; `build` (`completed`, `exitCode`, `stopped`, `answers`, `turns`, `durationSeconds`, `costUsd`, `cacheReadPerAnswer`, `costByModel`) ; `checks`, un objet par nom de contrôle joué, dans l'ordre du fichier, chacun `{ exitCode, stopped, durationSeconds, passed }` (`exitCode` vaut `null` quand le processus a fini sur un signal), `{}` sans contrôle ou si la construction ne passe pas ; `reviews`, un objet par nom de revue, dans l'ordre du fichier, chacune `{ model, verdict, exitCode, blocks, findings, costUsd, costByModel }` (`model` est celui demandé dans `step.json` ; `verdict` vaut `accept`, `request_changes` ou `invalid`, et un verdict invalide bloque), vide sans revue ou si la construction ne passe pas ; et, en haut, `outcome` (le verdict du round publié dans `record.json`), `costUsd` (la somme de chaque éclaireur, de la construction et de chaque revue jouée, les dollars additionnés tels quels, sans arrondi) et `costByModel` (la somme par modèle), puis `record`, le chemin `steps/<nom>/record.json` du dossier que l'étape a écrit dans le worktree (voir « Ce qu'une étape laisse dans le dépôt »).

Pour exploiter le résultat d’une session, l’hôte vérifie que son processus est sorti en 0, que son délai ne l’a pas interrompue et que le flux contient un résultat réussi. Un éclaireur en échec apporte zéro fait. Un constructeur en échec arrête le round avant les contrôles et les revues. Une revue en échec donne le verdict `invalid`, même si son flux a annoncé `accept`. Les nouveaux enregistrements de session conservent le code natif dans `exitCode`. Les enregistrements historiques restent lisibles sans ce champ.

Code de sortie : 0 si la construction a réussi, que tous les contrôles passent et qu'aucune revue ne bloque ; 1 sinon (aucun résultat d'éclaireur ne change cela) ; 2 pour les refus et pour un échec de l'outil (`ISOLATION_UNAVAILABLE`, …), écrit avec le préfixe `architect-os step:`.

### Ce qu'une étape laisse dans le dépôt

Quand l'étape sort en 0 ou en 1, et alors seulement, l'hôte écrit dans le worktree le dossier `steps/<nom>/`, où `<nom>` est le nom du dossier de l'étape (`^[a-z][a-z0-9-]{0,31}$`, sinon refus avant toute session, code 2). Une étape qui sort en 2 (refus, échec de l'outil) n'écrit rien. Un nom qui a déjà un dossier `steps/<nom>/`, quoi qu'il y ait, un lien pendant compris, est refusé avant toute session : un enregistrement ne se réécrit pas, une nouvelle passe prend un nouveau nom. Le mainteneur commite ce dossier avec le code de l'étape ; les flux, les rapports et les sorties des contrôles restent dans le dossier du poste.

| Fichier                                   | Contenu                                                                                                                                                                                                                                                                                                            |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `brief.md`, `step.json`, `scout.<nom>.md` | Les octets que l'outil a lus au départ de l'étape, jamais relus : une consigne retouchée pendant la construction est publiée telle qu'elle a été lue                                                                                                                                                               |
| `record.json` (`src/step-record.ts`)      | `step`, `startedAt`, `tree` (`commit`, `tree`, `clean`), `inputs` (SHA-256 de chaque fichier d'entrée), `launcher` (SHA-256 des fichiers du lanceur dont l'étape dépend), `sessions`, `checks`, `reviews`, `outcome` (`passed`, `refused`, ou `waiting` pour une étape routée), et pour une étape routée `routing` |

L'empreinte `tree` (`src/tree-fingerprint.ts`) est prise avant toute session : `commit` est `git rev-parse HEAD`, `tree` l'arbre git du répertoire de travail entier, suivi et non suivi, sans ce que `.gitignore` écarte (`git add -A` puis `git write-tree` dans un index temporaire, que l'index du worktree ne voit pas), et `clean` dit que cet arbre est celui du commit. `launcher` porte, pour `code.json` et, selon l'étape, `review.json` et `scout.json`, le fichier, le prompt et le profil qu'il nomme. Une session donne son rôle, son nom (sauf la construction), son modèle et son effort (pris de `step.json`), sa durée, son coût et son coût par modèle ; une clé de modèle du flux n'est gardée que si elle passe `^[a-z0-9][a-z0-9.-]{0,63}$`, sinon son coût est compté sous `other`. L'enregistrement ne porte aucun texte de session : ni constat, ni rapport, ni sortie de contrôle, ni chemin de l'hôte. Il n'est pas signé : il vaut ce que vaut le commit qui le porte (la porte, la revue, le ruleset).

Le profil `builder` refuse toute écriture sous `steps/` du worktree (`denyWrite`, et `Edit` refusé dans ses réglages) ; `publish` écrit en créant chaque fichier (`wx`, mode 0644) et refuse (code 2) si `steps` n'est pas un vrai dossier du worktree (un lien, un fichier) ou si `steps/<nom>` existe, ce qu'il revérifie au moment d'écrire. La porte relit chaque dossier (`features/descriptive/steps.feature`) : ses fichiers et rien d'autre, `step.json` et `record.json` conformes à leur schéma, `record.step` est le nom du dossier, et chaque empreinte de `inputs` est celle du fichier voisin.

**Rejouer une étape à la main** depuis son dossier : (1) créer un worktree au commit `record.tree.commit` ; si `record.tree.clean` est faux, l'étape est partie d'un arbre modifié, qui n'est pas rejouable depuis le dépôt seul (`record.tree.tree` permet de vérifier un arbre reconstruit) ; (2) copier `brief.md`, `step.json` et les `scout.<nom>.md` de `steps/<nom>/` vers un nouveau dossier hors du dépôt, sous un nouveau nom (le nom d'origine est pris) ; (3) depuis la racine de ce worktree, `"$LAUNCHER/aos" -- npm --prefix "$LAUNCHER" run step -- <ce dossier>`. Rejouer n'est pas reproduire : une session de modèle n'est pas déterministe ; ce qui se rejoue est l'entrée, et ce qui se compare est l'enregistrement.

### Les contrôles

`checks` de `step.json` (au plus 8, facultatif) nomme des commandes que l'hôte joue après la construction, sans modèle (`docs/design/orchestration-fable-5-2.md`, §13, O.3c) : `{ name, command, limitSeconds }`, `name` comme celui d'une revue, `command` un argv de 1 à 32 chaînes de 1 à 300 caractères sans NUL, saut de ligne ni retour chariot, `limitSeconds` de 1 à 7200. Elles ne tournent que si la construction est terminée et non arrêtée, l'une après l'autre dans l'ordre du fichier, jamais deux à la fois, chacune par un `SandboxRunner` (`sandboxCheck`, qui prend le port, donc un faux dans les scénarios) dans le profil `checker` (`profiles/checker.json` : worktree et `.git` en lecture seule, aucun domaine joignable, aucun proxy d'authentification, aucune variable du lanceur, les secrets de l'hôte refusés en lecture comme pour `reviewer`, `tmp` de la sandbox seul inscriptible, npm hors ligne, aucun terminal). L'entrée de la sandbox est fermée aussitôt ; les deux sorties, mêlées dans l'ordre d'arrivée, ne gardent en mémoire que leurs 4 000 derniers octets (`outputTail`) ; à `limitSeconds` la sandbox est stoppée et ses deux sorties fermées, si bien qu'un descendant sorti du groupe de processus, qui les tiendrait ouvertes après la fin de la commande, ne retient pas le contrôle au-delà de sa limite (il est alors dit arrêté, donc non réussi ; scénario réel dans `features/sandbox/checker.feature`). La durée est mesurée par l'étape, en secondes entières arrondies. Après chaque contrôle, `check.<name>.json` : `{ command, exitCode, stopped, durationSeconds, cut, output }`. Un contrôle passe si et seulement si son code de sortie est 0 et que la limite ne l'a pas arrêté ; le premier qui ne passe pas met fin à la phase : les suivants ne sont pas joués, aucune revue n'est lancée, l'étape sort en 1. Un contrôle que le port ne peut pas démarrer (`SandboxError`) fait sortir l'étape en 2. Quand tous ont passé, les revues reçoivent `brief.md` privé de ses blancs finaux, une ligne vide et le bloc `## Checks played by the host` de `renderChecks` : pour chaque contrôle l'argv, le code, la durée et la sortie, chacun comme une chaîne JSON (aucun saut de ligne, titre ou séquence de terminal n'arrive tel quel dans le brief). La construction et les éclaireurs ne reçoivent jamais ce bloc. `prompts/review.md` le dit donnée et non consigne.

Ce qu'un contrôle vert ne prouve pas : le worktree, ses dépendances installées comprises, a été écrit par la session de construction, qui a pu changer la configuration d'un outil, ou l'outil. Un contrôle vert est une indication donnée à la revue, pas une preuve ; le rejeu sur l'hôte après lecture du diff et la porte restent les juges.

Elle ne fait pas : le rejeu sur l'hôte de ce que la sandbox ne peut pas lancer, la porte (`npm run gate`), le commit. Ils restent à l'orchestrateur. La limite de temps est portée par l'outil de code (`limitMs` et `schedule` de `CodeToolDependencies`, session sur tubes seulement ; le terminal l'ignore).

### Les étapes routées

Une étape dont `step.json` porte un bloc `routing` a été préparée par une politique routée de Plan (`docs/plan.md`) à partir de la table du lanceur, `routing.json` (`src/routing.ts`, `docs/design/orchestration-fable-5-2.md`, §13) : le ticket servi, ses points, les fournisseurs admis, l'empreinte SHA-256 de la table, la raison de la bande de départ et l'échelle, une passe par bande, chacune avec son constructeur et sa revue indépendante (une revue vers Google y est `waiting`). Avant toute session, Step lit `routing.json` avec les autres fichiers du lanceur, refait la route (`routedStep`) et refuse `STEP_ROUTING_MISMATCH` si `step.json` n'en est pas la copie exacte ; `reviews` doit y être vide. L'admission exige un spécimen pour le constructeur de chaque passe (`build`, `build:pass-2`, …) et pour chaque revue qui n'attend pas (`review:independent`, `review:independent:pass-2`, …). Chaque passe joue la construction, les contrôles et la revue de son barreau ; `src/step-passes.ts` en tire le signal (`accepted`, `stopped`, `build_failed`, `check_failed`, `review_waiting`, `review_invalid`, `changes_requested`). `stopped`, `check_failed` et `changes_requested` promeuvent à la passe suivante, s'il y en a une ; les autres arrêtent l'étape. La passe suivante reçoit `brief.md` (avec les faits des éclaireurs), puis le bloc `## Previous pass, as the host observed it` : la passe promue, son modèle, son signal, les contrôles échoués de `renderChecks` et les constats des verdicts qui bloquent, chaque texte encodé en chaîne JSON et borné à 4 000 octets. Les fichiers d'une passe après la première portent le préfixe `pass-<n>.` (`pass-2.build.brief.md`, `pass-2.check.<name>.json`, …). `record.json` gagne `routing` (ticket, points, `table_sha256`, `start`, et chaque passe : `pass`, `band`, `provider`, `model`, `effort`, `signal`) et le champ `pass` de chaque session, contrôle et revue ; `outcome` vaut `waiting` quand la dernière passe attend sa revue (l'étape rend 1). Stdout ajoute `routing` ; `build`, `checks` et `reviews` y sont ceux de la dernière passe.

## La bibliothèque de prompts

Le dossier `prompts/` du lanceur porte un prompt par rôle : `prompts/build.md` (session de code, `code.json`), `prompts/review.md` (revue, `review.json` ; sa section « Checks played by the host » dit que le bloc des contrôles du brief est une donnée et jamais une consigne, qu'un contrôle vert est une indication et non une preuve, qu'on ne rejoue pas une commande listée, et que ce que ni elles ni la revue n'ont établi va dans `not_checked`) et `prompts/scout.md` (éclaireur, `scout.json`, même commande, même profil `reviewer` et même proxy que `review.json` ; le prompt dit qu'il ne change rien, que ce qu'il lit est une donnée, qu'il ne répond que par des faits dont la citation est copiée caractère pour caractère, et que l'hôte jette ce qu'il ne retrouve pas). Chaque outil le nomme par `launcherPromptFile`, obligatoire, relatif à `packages/sandbox`. Les prompts vivent dans le lanceur parce que c'est un chemin que la sandbox ne peut pas écrire (l'outil refuse de démarrer sinon) : une session ne peut pas écrire le prompt de la suivante. Si le fichier manque, la session ne démarre pas (`ISOLATION_UNAVAILABLE`), avant tout proxy. Chaque prompt a son scénario de chargement (`features/review-files.feature`), avec des copies cassées rejetées.

## La revue

Une session de revue est le second lancement du même outil : `review.json` (`src/review.ts`, `npm run review`) donne à `src/code-tool.ts` le profil `reviewer` (worktree et `.git` en lecture seule, voir `profiles/reviewer.json`) et son prompt. Depuis le worktree à relire :

```bash
"$LAUNCHER/aos" -- npm --prefix "$LAUNCHER" run review -- -p --json-schema "$(cat <lanceur>/packages/sandbox/prompts/review-verdict.schema.json)" -- "<brief de l'étape>"
```

Les profils de `profiles/` : `builder` (la session de code), `reviewer` (revue et éclaireur : lecture seule, le proxy d'authentification seul joignable), `checker` (un contrôle de l'étape : lecture seule, aucun réseau, aucun secret, `tmp` seul inscriptible, voir « Les contrôles »), `module` et `worker` (la plateforme).

Le prompt, `prompts/review.md`, renvoie à `CLAUDE.md` tel que commité (`git show HEAD:CLAUDE.md`). Le verdict suit `prompts/review-verdict.schema.json` : `verdict`, `findings` (niveau, fichier, ligne, citation, raison), `not_checked`.

Le `settings.json` de la session porte aussi `permissions.allow` (`Bash`, `Read` et `Edit` dans le worktree pour `builder` ; `Bash` et `Read` pour `reviewer`), car depuis Claude Code 2.1.325 `-p` refuse toute commande qu'aucune règle n'autorise ; les règles `deny` l'emportent. Les profils fixent aussi `TMPPREFIX` sur le `tmp` de la sandbox, car zsh écrit sinon ses here-documents sous `/tmp/zsh`, que la sandbox ne peut pas écrire.

Le parent `<tmp>/aos-sb` est créé sans `recursive` puis vérifié par son chemin réel et `stat` : s'il n'est pas un vrai dossier (un lien symbolique est refusé), de l'uid courant, de mode exactement 0700, le démarrage est refusé (`ISOLATION_UNAVAILABLE`), car sous Linux `/tmp` est partagé et un autre utilisateur pourrait l'avoir créé avant. Les dossiers sont courts (`aos-sb/s-XXXXXX`, canari `c-XXXXXX`) : srt écoute sur un socket Unix dans le `tmp` de la sandbox (`srt-mux-<pid>-<n>.sock`), dont le chemin tient en 103 caractères sous macOS jusqu'à 26 ; si `<dossier>/tmp` dépasse 79 caractères, le démarrage est refusé (`ISOLATION_UNAVAILABLE`).

Refus sans repli : srt absent, canari qui lit son fichier secret ou joint le port de l'hôte, chemin de confiance inscriptible, répertoire hors d'un worktree lié, identifiant de l'hôte illisible (`ISOLATION_UNAVAILABLE`, `NOT_A_WORKTREE`).

## Les natifs de la conception

Le broker et `data` tournent hors de srt, enfants de la gateway (conception, §2, « Pourquoi quatre natifs »). `src/native-launcher.ts` les lance, et rien d'autre : une liste fermée, copiée à la construction, d'un nom, d'un dossier de travail, d'un argv et de variables. Rien n'est hérité de l'environnement de l'appelant, pas même `PATH` : le dossier et `argv[0]` sont des chemins absolus. Pas de shell.

Ce n'est pas un adaptateur du port `SandboxRunner`, et c'est voulu : il n'isole rien. Ni le lanceur ni ses enfants n'ont les types du port (un enfant natif n'a pas de `stop()`), donc le compilateur les refuse là où une sandbox est attendue, l'hôte des modules ou celui des workers ; deux affectations marquées `@ts-expect-error` dans `features/steps/native-launcher.ts` le tiennent à chaque `tsc -b`. Aucun contenu non fiable ne passe par lui.

`close()` ferme l'entrée de l'enfant, que le broker et `data` lisent comme le départ de leur parent : ils ferment leur écoute ou leur base et sortent. Un enfant encore là après le délai de grâce a tout son groupe de processus tué. Le lanceur lit lui-même la sortie d'erreur de l'enfant et la remet à un journal avec son nom : un enfant dont personne ne lit la sortie d'erreur se bloque une fois le tube plein, et ne verrait jamais la fin de son entrée. Pas de plafond de sortie : ces enfants parlent MCP à leur parent pendant toute la vie de la gateway.

## Codex in Docker SBX

An admitted Step chooses Codex with this construction specification. Its scouts, checks, reviews and publication keep their existing Step entry points.

```json
{ "build": { "provider": "openai", "model": "gpt-6.2-sol", "effort": "medium", "limitSeconds": 600 } }
```

The other supported model is `gpt-6.2-astra`. Build effort accepts `low`, `medium`, `high` and `xhigh`. An omitted builder provider selects Claude. Reviews in Step currently run Claude under SRT. Step refuses a Claude build with a correctness review before any session starts. It recognizes the explicit review dimension `correctness` and the legacy names `correctness` and `justesse`. A Gemini re-reading runs separately through Google’s native agent.

The host requires the exact SBX CLI, shell kit and template digest in [the SBX policy](sbx/isolation.json). Put the pinned Linux ARM64 archive at `$ARCHITECT_OS_RUNTIME_ROOT/cache/sbx/codex-0.170.0-linux-arm64.tgz`. Use a trusted launcher outside the target worktree. The host and guest check the archive before extraction. The isolated guest also checks the native executable’s digest, version and UID before sending a request.

Create `state/sbx` under the admitted runtime with mode 0700. In that directory, `limits.json` (mode 0600) takes three positive integer fields. `requests` counts all dispatched calls, `bytes` counts request and response bodies together, and `tokens` counts terminal input plus output tokens. Choose all three for the account and work assigned. A tool turn can require several requests. SIWC reports tokens after generation. An over-budget terminal stops the run, and a request already sent can consume more than the remaining token allowance. [SIWC limits](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

Establish the account once at installation with `./aos -- npm run sbx:sign-in -- gpt-6.2-astra` (Sol is also accepted). Only that explicit command prints a loopback link for PKCE sign-in. Step reads the OS credential store through the host process. macOS uses the signed-in user’s Keychain and Linux requires an available freedesktop Secret Service. The account entry uses service `architect-os.siwc` and the installation’s opaque host ID. It contains the access, refresh and ID tokens, absolute expiry, granted scopes, verified model, issued client ID and verified subject digest, nonce, issue time and authentication time. A rotating grant may also hold the pending ID token and its receipt time. The host resumes signature and account verification before using that bearer, even after a process restart. The private runtime state contains the host ID, public registration binding and a lock with no token data. An exclusive SQLite transaction serializes credential replacement across processes. The OS releases the lock when a process exits. The explicit installation command can reauthorize the same account after revocation. A Step reports `SBX_SIGN_IN_REQUIRED` if the grant is missing or revoked. The owner can then run the installation command. [OpenAI account and session rules](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) · [Keychain and Secret Service backend selection](https://github.com/Brooooooklyn/keyring-node#linux-backend-selection)

The host user’s unlocked store is the trust boundary. Other native applications authorized by that OS account may have access. SRT restricts Keychain files and VM mounts exclude the host home and session bus. The offline native Step creates an exclusively named synthetic Keychain item in a separate installation process, reads it from the host, checks that an SRT session cannot retrieve its value and removes it. The Linux backend requires its service for the logged-in host user. Linux native-store acceptance requires a Linux host with that service.

`state/sbx/usage.jsonl` contains host metering metadata. The pinned client calls `http://host.docker.internal:<port>/v1/responses` through Docker’s guest HTTP proxy. SBX grants this VM one POST route to host loopback and TCP to `registry.npmjs.org:443` when the frozen SRT builder profile admits the registry. The host inspects the rules, mounts and guest daemon socket before staging. A guest canary checks the permitted route, a different method on it, an unlisted path, an unlisted host and a second listening host port. It repeats the two destination checks with proxy discovery disabled. Only the initial run specification and final receipt use standard input and output. The native client reads its single-run bearer from a guest FIFO via its provider authentication command. [Docker host-service addressing](https://docs.docker.com/ai/sandboxes/workflows/development/) · [Scoped HTTP rules](https://docs.docker.com/ai/governance/local/network-rules/)

The retained build stream nests native claims under `guest` and includes the host’s VM removal receipt. The final native agent message is retained in the private Step build report. The Step record includes the selected provider, model, effort, client version, binary digest and observed response usage. The monetary cost of subscription inference is unknown.

## 1. Objectif

Réduire le contexte et les tokens consommés par tâche (objectif unique de v3), avec un seul chemin d'exécution pour le produit, le développement et la CI. À la brique 3, le client verra trois méta-tools ; il écrira du code ; l'exécuteur appellera les modules, filtrera, et ne rendra qu'un résultat borné. Aujourd'hui, le client appelle les tools du contrat, `recall` et `remember` (`TOOL_NAMES`, `gateway/src/presentation/mcp-server.ts`), et la gateway ouvre une task par appel. Le produit reste la v3. Seule sa réalisation change : un conteneur v3 devient un processus srt.

Mesures v3 : M1, tokens de contexte client par tâche, en baisse ; M2, tokens totaux par couche et par modèle, jamais en hausse quand M1 baisse ; définitions ≤ 1 500, recall ≤ 600, résultat de tool ≤ 1 000 tokens ; R = 1 − T(code execution) / T(orchestration directe), mesuré sur les mêmes tâches en brique 3. Aucune ne bloque une porte tant que le propriétaire n'a pas fixé la date de la baseline de M1 et M2 (D-7).

**Pourquoi quatre natifs.** Un processus sous srt ne sert pas de listener joignable par l'hôte : macOS `EPERM`, Linux `ECONNREFUSED` [T-39b, T-07]. D'où gateway et broker. Sous Linux, `allowUnixSockets` est ignoré (README srt), donc `data` et Postgres, joints par socket Unix, restent natifs ; ce montage est prouvé [E-09]. La gateway lance tout le reste, modules et workers, sous srt ; les plugins relèvent de la brique 1c. Hors de la plateforme, la porte de CI exécute encore le code candidat sous le compte de l'hôte : sa mise sous sandbox est à concevoir (README, « The gate under the sandbox »). Le reverse proxy de v3, Caddy, sera natif devant la gateway et n'exécutera aucun contenu non fiable (brique D) ; aujourd'hui `deploy/edge/Caddyfile` n'en est qu'un exemple, en HTTP, que rien dans l'arbre ne lance. Correspondance avec la figure 1 de v3 : §9, A.

**MCP, aucun protocole maison.** Les liens internes sont MCP avec le SDK officiel : sur le stdio de l'enfant entre la gateway et `data`, le broker, chaque module et chaque worker ; sur HTTP en boucle locale pour le rappel d'un module vers la gateway, par le proxy srt (`gateway/src/presentation/callback-host.ts`, « Identifiant d'appel » ci-dessous). Le worker joint le broker en HTTP, par l'API des messages. Un module est serveur MCP, la gateway est son client [E-01, T-38] ; le broker aussi (§2, Broker). Le worker est client MCP sur ses propres stdin/stdout, la gateway est serveur sur les flux de l'enfant, parce qu'il appelle des tools et que MCP ne permet pas l'inverse [E-02 : 1 000 allers-retours en 45 ms sous srt, 38 ms sans] ; l'executor de la brique 3 suivra ce montage. Son identité est la fermeture du handler : un `_meta.task` forgé est ignoré, un enfant hostile n'abat pas l'hôte [E-03]. `query()` et le binaire vivent dans la même sandbox [T-41, deux OS, faux amont]. `type: http` vers un module est refusé par schéma [prouvé : `manifest.feature`, 1b.4 ; MCP sur le stdio de chaque module, identifiant dans `_meta`, relance puis `SERVICE_UNAVAILABLE` après 3 lancements de suite sans réponse : `features/integration/gateway.feature`, 1b.4, journal §28 ; le serveur MCP de la gateway sur les flux du worker (`task_input`, `call`, `task_complete`) : `gateway/features/worker-host.feature`, `features/integration/agent-worker.feature` et `features/sandbox/recall.feature` sous vrai srt, 1b.5, journal §29 ; celui de l'executor : brique 3].

**Identifiant d'appel.** À chaque `tools/call` vers un module, la gateway crée un identifiant opaque aléatoire (`randomUUID()` de `node:crypto`, `gateway/src/infrastructure/mcp-routing.ts`), sans signature : il ne vaut que par la table en mémoire de la gateway ; elle le passe dans `_meta` et le relie en mémoire à {task, parent, profondeur, échéance} ; elle l'invalide au retour. Le module le présente à son rappel, par le proxy srt vers le port de rappel que la gateway écoute en `127.0.0.1` (choisi par le système au démarrage et donné au profil `module`, `${callbackPort}`) [T-38] ; inconnu ou invalidé : `401`. La gateway en tire la task, le parent et l'identité du module appelant, dont le profil est son `calls_allowed` : `task` ne vient jamais d'un argument. Un module n'est joignable que par son parent, sur stdio. **Bornes le long du DAG** : l'identifiant porte la profondeur (parent + 1, refus au-delà du maximum du profil client) et l'échéance (min de celle du parent et du `timeout_ms` du module ; au premier niveau, le parent est la task, dont l'échéance est son délai maximal, étape 2) ; à l'échéance, la gateway annule l'appel et invalide l'identifiant. Les tokens ne se dépensent qu'au broker, par task. Un appel sans modèle est donc borné par son échéance, sa profondeur et le nombre d'appels de sa task, pas par des tokens. `max_result_tokens` est déclaré au catalogue et validé par son schéma ; la gateway ne l'applique pas encore et relaie le résultat sans le réduire (résumé et handle : brique 2). Aucun plafond d'octets n'est posé sur la lecture du flux MCP d'un module ou d'un worker (`gateway/src/infrastructure/stream-transport.ts`). [prouvé, routage par l'identifiant d'appel, profondeur, échéance du parent, identifiant invalidé : `gateway/features/gateway.feature`, 1b.4, journal §28 ; le transport du rappel, MCP sur HTTP en `127.0.0.1` par le proxy srt, l'identifiant d'appel en jeton porteur, `401` sinon, et le profil srt `module` : `gateway/features/callback-host.feature`, `modules/memory/features/memory-module.feature`, `features/sandbox/recall.feature`, 1b.5, journal §29]

**Broker.** Le worker reçoit `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>` et un jeton de task aléatoire comme `ANTHROPIC_API_KEY` : il n'a jamais la vraie clé [E-05, T-23, T-41]. Un seul listener ; son port est le `port` du fichier de configuration du broker (`BROKER_CONFIG`, `modules/broker/broker.json` dans l'arbre), que la gateway lit et donne au profil `worker` (`${brokerPort}`). Ordre, une règle : la gateway passe {jeton, task} au broker (le protocole du broker admet aussi un parent, que la gateway ne passe pas aujourd'hui) par un `tools/call` MCP sur le stdio du broker (son enfant natif, lancé avant tout worker, serveur MCP pour elle), puis lance le worker ; à la fin de la task, un second `tools/call` retire le jeton. Le broker résout le jeton vers une task connue (`401` sinon), puis construit la requête amont : avec la configuration commitée, seuls `POST /v1/messages` et `POST /v1/messages/count_tokens` passent (`routes`), vers le seul `api.anthropic.com` (`upstream` ; le chargeur exige un amont HTTPS, l'opérateur peut en nommer un autre par `BROKER_CONFIG`), avec l'identifiant de son fichier dans un seul en-tête et le corps inchangé : une clé d'API dans `x-api-key`, ou, quand `scheme` de `broker.json` le dit, un jeton d'accès de courte durée en `Authorization: Bearer` (17 novembre 2026, journal §86). Les autres chemins répondent `403`. Le jeton ne protège pas d'un natif déterminé (R-3) ; il évite qu'un processus local quelconque dépense la clé en joignant le port, et il attribue le coût à une task. [prouvé : `modules/broker/features/broker.feature` et `broker-start.feature`, 1b.2 ; appel réel, requêtes invalides comprises (T-04R) : `.github/workflows/broker-live.yml` (`npm run broker:live`), sur `main` seulement, sans clé d'API ni jeton d'accès de longue durée stocké : le job échange le jeton d'identité de son exécution contre un jeton d'accès de quelques minutes (voir « Identifiant de la preuve réelle ») ; hors porte (`gate.yml` sans secret, §7) ; `modules/broker/features/broker-scheme.feature` pour l'envoi en `Bearer`]

**Identifiant de la preuve réelle : fédération d'identité, pas de clé (17 novembre 2026, journal §86).** Proposée par le propriétaire au moment de créer une clé. Aucun secret de longue durée n'existe : GitHub signe l'identité de l'exécution, Anthropic l'échange contre un jeton qui expire en dix minutes, d'après une règle que le propriétaire a créée dans sa console. C'est aussi le mécanisme prévu pour un broker sur site, avec un autre émetteur.

**Mesure du coût, pour la traçabilité et la prévision seulement** (décision 11). Aucun plafond, aucune réservation, aucune coupure ni aucun refus pour raison financière. Au retour de chaque réponse amont, le broker enregistre `usage` (tokens d'entrée, de sortie, de cache lu, de cache écrit), le modèle, la task (tirée du jeton), l'identifiant d'appel parent quand il est reçu avec le jeton (la gateway ne le passe pas aujourd'hui, §2, Broker) et l'horodatage. Il remonte l'enregistrement à la gateway sur son stdio, par une notification MCP standard (`notifications/message`, logger `usage`), et la gateway l'écrit par `data`, comme à l'étape 11 : un seul parent stdio par processus, aucun lien broker → `data`. `data` le persiste au registre, en append-only sous Postgres ; avec le store `memory`, il ne garde rien après l'arrêt. `usage` couvre aujourd'hui ce qui passe par le broker, la couche `broker`. La couche client et M1 (tokens de contexte client) viendront du hook M1 de la brique 1c ; M2 agrégera les deux, par task, par couche et par modèle, et Mission Control la lira (brique 7). Une réponse interrompue avant `usage` n'a pas d'enregistrement : la facture fait foi. L'indisponibilité de `data` est détectée à l'échec du `tools/call` de la gateway vers `data` ; les nouveaux appels sont refusés (jetons retirés par le même `tools/call`, d'où `401`), les enregistrements reçus entre-temps sont perdus (R-9) ; après retour de `data`, la gateway réémet les jetons. [prouvé côté broker : `broker.feature`, 1b.2 ; prouvé côté gateway et `data` : `features/integration/usage.feature`, `gateway/features/usage-forwarder.feature`, `data/features/*.feature`, 1b.3, journal §27 ; la couche, `broker` ou `client`, est posée par l'écrivain, la gateway pour le broker ; la sonde du retour de `data` est une lecture de son store, `usage.aggregate`]

[…] La boucle d'orchestration pourrait évoluer pour utiliser les 4 modèles au lieu de gérer les coûts par une borne de temps. Pareil pour la boucle de vérification. Elle pourrait évoluer pour paralléliser et utiliser les 4 modèles. » C'est la décision 11 : le coût se mesure, il ne se plafonne pas. Un délai ou un nombre de tours est un fusible contre une session qui s'emballe (décision 12), pas une gestion du coût. Ce que ces chiffres disent : le volume est dans le contexte relu à chaque réponse, pas dans ce que le modèle écrit ; la revue coûte plus que la construction, et chaque relance repaie les deux ; tout le travail d'une session est payé au prix d'un seul modèle, quelle que soit sa difficulté (dans la revue de l'outil de veille, 29 appels d'outil sur 44 étaient des lectures de fichiers et 13 des lancements de commandes). La cause se traite par le routage : chaque unité de travail au modèle le moins cher qui sait la faire, en parallèle quand les unités sont indépendantes. Mesuré le même jour : une session lancée en `--bare` n'a aucun outil de délégation ; le routage se fait donc par l'hôte, une session par phase, ce qui est la forme de la boucle (`docs/design/orchestration-fable-5-2.md`, où la table de routage restait à écrire au moment de ce relevé ; son §13 la donne depuis le même jour, `db9a6d41`, encore à mettre en œuvre).

**Bornes opérationnelles** (décision 12) : une task peut toujours être interrompue, et aucune boucle ne tourne indéfiniment. Le profil client fixe, à l'ouverture de la task (étape 2), son délai maximal, dont dérivent les échéances des appels, et son nombre maximal d'appels de modules, toutes profondeurs, en plus de la profondeur maximale ; un agent a en plus `maxTurns` (`max_turns` du manifeste), second rempart côté SDK. Précédence : entre l'échéance du parent, le `timeout_ms` du module et celui de l'agent, le plus court gagne. Une borne atteinte, ou l'annulation par le propriétaire (un appel à la gateway, tool de son seul profil, hors du catalogue des clients), a l'effet de `task_complete` : la gateway invalide les identifiants d'appel et le jeton de la task et tue ses groupes srt (`kill(-pgid)`). Un module, partagé entre tasks, n'est pas tué : son appel en cours est annulé et son identifiant invalidé. Une fin par borne ou par annulation n'atteint ni `verify` ni verdict ; le registre porte la fin de task (terminée, délai, nombre d'appels, annulée, erreur) et le client reçoit l'erreur correspondante. L'annulation est construite dans le routeur (`TaskRouter.cancel`, refusée hors du profil propriétaire) ; le serveur MCP des clients n'expose pas encore de tool d'annulation. Ce tool prendra la task cible en argument, ce qui ne contredit pas « task ne vient jamais d'un argument », qui vise l'identité de l'appelant. La concurrence sera un compteur en mémoire de la gateway, écart accepté au « stateless » de v3 ; dans `data`, il coûterait une écriture par appel et fuirait à chaque arrêt brutal. Aujourd'hui la gateway ne compte pas la concurrence : elle garde en mémoire les tasks ouvertes et les sandboxes vivantes, applique un quota d'appels par sujet, par tool et par minute, et tue les sandboxes vivantes à son arrêt, au plus tard à la borne de l'arrêt (`gateway/src/main.ts`, `serveNative`). Les sandboxes sont des groupes de processus détachés : après un arrêt qui ne peut pas être intercepté (`SIGKILL`), `data` et le broker finissent avec leur entrée standard, mais une sandbox peut rester (`docs/operating.md`). [prouvé, délai, nombre d'appels et annulation : identifiants invalidés, appels en vol annulés, jeton retiré, sandboxes de la task arrêtées, fin au registre, aucun module atteint ensuite : `gateway/features/gateway.feature`, 1b.4, journal §28 ; `maxTurns` : `gateway/features/agent-tools.feature` et `features/integration/agent-worker.feature` (arrêt réel du SDK), 1b.5, journal §29]

**Organisation du dépôt.** Marketplace à la racine : `.claude-plugin/marketplace.json`, dont la liste de plugins est vide depuis que la décision 2 (4 novembre 2026, `000a540e`) a retiré `plugins/builder-guard` ; la distribution de plugins relève de la brique 1c. Plateforme : `gateway/`, `data/`, `modules/`, `services/`, `packages/{contracts,sandbox}`. Descriptif : `topology/catalog.json`, `topology/modules.mcp.json` (format `.mcp.json`), `topology/clients.json`, `agents/*.md`, les profils des sandboxes (prévus le 30 octobre 2026 dans un gabarit unique `sandboxes/base.srt.json`, jamais créé ; ils sont cinq fichiers sous `packages/sandbox/profiles/`, §5). Les manifestes par module (`modules/*/manifest.yaml`) et `manifest-registry`, qui en tirerait le catalogue, ne sont pas construits : le catalogue est écrit à la main et commité (§5, Manifeste de module). Le nom provisoire vit dans `platform.json` ; aucun scénario ne vérifie encore que le littéral reste dans la liste dérivée.

## 3. Parcours d'un appel `execute`

Ce parcours est la cible du front de code de la brique 3, non construit. Aujourd'hui, la gateway ouvre une task par appel d'un client à `recall` ou `remember` et la route vers le module ou le worker qui sert ce tool ; il n'y a ni executor, ni `verify`, ni réduction du résultat par `max_result_tokens`.

| #   | De → vers                   | Quoi                                                                                                                                                                            |
| --- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Client → gateway            | `execute(script)`, un des trois méta-tools (`search`, `describe`, `execute`)                                                                                                    |
| 2   | Gateway                     | Auth, profil client, compteur de concurrence ; ouvre la task, sa `trace` et son `parent` (nul pour un appel client), son délai maximal et son nombre maximal d'appels           |

| 6   | Gateway → module            | Profil, `calls_allowed`, profondeur contrôlés ; identifiant d'appel créé ; `tools/call` sur stdio ; le module exécute sous srt                                                  |
| 7   | Module → gateway → executor | Résultat typé, jamais au client ; `max_result_tokens` du module                                                                                                                 |

## 4. Modèle de confiance et risques acceptés

**Portée.** Le poste du propriétaire, un seul uid ; puis des utilisateurs fiables. srt n'est ni une VM ni un conteneur renforcé : noyau partagé, préversion annoncée. Du contenu hostile multi-tenant est hors portée ; le jour où le besoin existe, c'est une décision du propriétaire (VM à évaluer, candidats au journal), pas une évolution de ce document. Moindre privilège : un profil par sorte de processus (§5) ; sur serveur, un uid propre au broker, seul détenteur de la clé, et un uid que gateway et `data` peuvent partager (R-8) ; aucun identifiant Postgres, aucune lecture de secret par un agent de conception ou de CI.

**Règles de refus : une couche de réduction, à côté de srt, pas une frontière.** Pour l'outil 1a.0, Claude Code tourne en `--bare` (le mode par défaut annoncé de `-p`) : il ne charge ni hooks, ni plugins, ni skills, ni serveur MCP, ni CLAUDE.md, et chaque entrée est passée explicitement. Mesuré sur Claude Code 2.1.314 (journal, §19) : sous `--bare`, un hook ne tourne ni depuis un plugin de `--plugin-dir`, ni depuis `--settings`, alors que `permissions.deny` de `--settings` s'applique. Les refus de l'ancien plugin `builder-guard` sont donc des règles `permissions.deny` du `settings.json` de la session, écrit par le lanceur, passé par `--settings`, que la sandbox ne peut pas écrire (`denyWrite`) : `git push`, `git config`, `security`, lecture et écriture des fichiers de secrets, écriture de `.git/hooks` et `.git/config`. Un Bash obfusqué ou un script lancé par `npm test` leur échappe : elles réduisent le risque, srt le ferme. Les workers de plateforme n'en dépendent pas (`settingSources: []`).

**Un gabarit par sorte, pas dix fichiers.** Aujourd'hui, cinq fichiers de profil sous `packages/sandbox/profiles/`, un par sorte de processus lancé sous srt, portent chacun ce qui ne varie pas pour sa sorte : `builder` (une session de construction, 30 octobre 2026), `worker` et `module` (le processus d'une task et celui d'un module, 6 novembre 2026), `reviewer` (une session de revue, 14 novembre 2026) et `checker` (une commande de contrôle, sans modèle, 17 novembre 2026) ; la conception du 30 octobre 2026 prévoyait un seul gabarit, `sandboxes/base.srt.json`, qui n'a jamais été créé ; le JSON ci-dessous est ce gabarit, proposé le 30 octobre 2026 et gardé comme tel. Il n'y a pas de fusion : l'adaptateur charge le gabarit nommé par la requête (`loadTemplate`, `packages/sandbox/src/profile.ts`), y résout ses propres variables (`${home}`, `${runtime}`, `${repo}`, `${worktree}`, `${worktreeName}`, `${tmp}`, `${config}`, `${sandboxes}`, `PROFILE_VARIABLES`) et celles du lanceur (`${callbackPort}` pour un module ; `${brokerPort}` et `${taskToken}` pour un worker ; `${authProxyPort}` et `${sessionToken}` pour une session de la boucle), valide le résultat avec un schéma zod strict, l'écrit hors des chemins inscriptibles et le passe à srt par `--settings` (`packages/sandbox/src/srt-runner.ts`). Aucun réseau n'est dérivé d'un manifeste : l'allowlist est celle du gabarit. Le module et le worker ont chacun un cwd jetable, créé dans le dossier de leur sandbox au lancement et retiré à l'arrêt ; un module sert plusieurs tasks dans le même cwd, d'où `realpath` sous le dépôt de la task (§3, brique 4). Les sessions `builder`, `reviewer` et `checker` partent du worktree. Conçus et non construits : le cwd jetable d'un executor par session (brique 3) et le dossier de sortie persistant de `manifest-registry`, nommé dans son profil, hors de son cwd jetable.

**Ce que le banc impose, chaque point nommant un échec réel :**

- Schéma strict : srt tolère une clé mal écrite, `strictAllowlistt` passe sans erreur [T-01]. Le schéma refuse aussi les options d'affaiblissement (§4.1).
- `denyWrite` nommés : sous Linux, srt ne protège que ce qui existe au lancement [T-02e, T-02e2] ; nommés, ils tiennent [T-02e4, T-02e5, T-02e6].
- Un dossier temporaire par sandbox, `CLAUDE_CODE_TMPDIR` et `allowWrite` (écriture en plus), retiré à l'arrêt : srt fixe `TMPDIR` sans le créer, le binaire et `tsx` échouent, et le poste donnait un faux vert (runs 41037109539 et 41037711860).
- `NO_PROXY` retiré de l'environnement du worker, sinon le loopback contourne le proxy et se fait refuser [T-03, T-41].
- srt installé hors de tout chemin inscriptible (README srt, « Where This Package Is Installed »).

**Profils de task.** `agents/<nom>.md`, format Claude Code, chargés par `query({ agents })` : par `plugins`, le corps du prompt n'atteint pas le modèle [E-08]. À la brique 5, un agent de la plateforme qui modifie du code travaillera dans un worktree, écriture en plus, comme la session `builder` de 1a.0 (R-2) ; un agent en lecture n'aura que `allowRead` sur le dépôt. Le worker du seul agent d'aujourd'hui, `memory`, n'écrit que son cwd jetable, son dossier de configuration et son dossier temporaire (`packages/sandbox/profiles/worker.json`).

**Manifeste de module.** Conçu, non construit : lu par `manifest-registry`, module sous srt, qui générera les modules importables (lus par l'executor) et le catalogue ; la gateway ne lira que cette sortie. Aujourd'hui, la gateway valide ensemble, par les schémas de `packages/contracts`, le catalogue commité, écrit à la main (`topology/catalog.json`), les commandes des modules (`topology/modules.mcp.json`) et les profils clients (`topology/clients.json`) (`gateway/src/infrastructure/topology-files.ts`) ; une topologie invalide est refusée entière : aucun module lancé, rien routé.

Le mode `catalog`, qui servira les clients sans exécution, relève de la brique 2.

## 6. Port `SandboxRunner`

> Le mode Docker décrit dans cette section a été retiré le 16 novembre 2026 (décision 22, journal §63) : srt est le seul moyen d'isolation. Le texte reste comme trace de ce qui a été construit et mesuré.

```ts
interface SandboxRunner {
  start(request: SandboxRequest): Promise<Sandbox>;
}
// SandboxRequest : { profile, cwd, command }, un gabarit nommé, un dossier de travail, un argv statique
// Sandbox : { stdin, stdout, stderr, exited, stop() }, trois flux, la fin du processus et un arrêt
```

Un seul port, dans `packages/sandbox/src/port.ts`, et un seul adaptateur, `SrtSandboxRunner`, appelés par la gateway et par les outils de la boucle (`code`, `review`, `step`). L'outil de code interactif passe par une seconde entrée du même adaptateur, `runInTerminal`, hors du port, qui donne à la TUI les terminaux de l'appelant. C'est le lieu de lancement, et il n'a que cinq règles :

- La signature n'accepte aucun contenu : l'entrée arrive ensuite sur stdin (`task_input` pour un worker).
- `spawn` sans shell, argv statique, environnement en liste fermée.
- `stdio` est la constante `['pipe', 'pipe', 'pipe']`, sans paramètre : un socket d'écoute passé en fd 0 servirait sous Linux [T-07-fd0], et aucun appelant ne peut en passer ; `runInTerminal` hérite des descripteurs de l'appelant, après avoir vérifié que tous trois sont des terminaux.
- `detached` et `kill(-pgid)`, jamais `kill` sur `srt` seul, qui laisse des descendants (10 sur 11 sous Linux) [T-06].
- `stdin.on('error')` dans l'adaptateur ; `maxBufferSize` et plafond d'octets sur toute sortie lue, règle posée par le banc (l'hôte tombait sans [E-02, E-03]), tenue aujourd'hui aux seuls points de lecture qui l'appliquent : la sortie du canari, la fin gardée de la sortie d'un contrôle d'étape. Le flux MCP qu'en lit la gateway n'a pas encore de plafond (§2, Identifiant d'appel).

Garde : `@anthropic-ai/sandbox-runtime` ne s'importe que dans `packages/sandbox`, sans exception ; `child_process` aussi, avec trois exceptions nommées dans `.dependency-cruiser.cjs`, hors de la plateforme : `git.ts` et `replay.ts` de la porte (`tools/test-gate/src/infrastructure/`) et `host-process.ts` de la livraison (`tools/deliver/src/infrastructure/`) ; règles dependency-cruiser et fixtures ; l'infrastructure d'un composant peut importer le port, son domaine et son application non (prouvé : `features/arch/guard.feature`, brique 1b.1).

**Adaptateurs.** srt par défaut. Docker seulement là où srt n'est pas supporté, par un champ de configuration explicite, jamais par détection ni bascule (décision 18). L'adaptateur d'origine (`packages/sandbox/src/docker-runner.ts`, repris de la première réalisation, un réseau Docker d'exécution) reste tant que la première réalisation s'en sert.

**Docker sur le chemin natif (brique 1b.6b, conçu le 15 novembre 2026 ; l'adaptateur et son contrôle au démarrage sont construits, `packages/sandbox/src/docker-process-runner.ts`, journal §51 et §52 ; la gateway native le choisit par configuration et le contrôle avant de lancer quoi que ce soit, journal §53 ; l'adaptateur réel est mesuré devant un vrai démon, journal §54 ; le bout en bout et le test d'évasion sont joués devant un vrai démon sans root en CI sur Linux, journal §55).** Une architecture, deux moyens d'isolation : la gateway, `data` et le broker restent des processus natifs ; seuls les modules et les workers, que srt isole ailleurs, tournent en conteneur. Les mêmes gabarits (`packages/sandbox/profiles/module.json`, `worker.json`) pilotent les deux adaptateurs.

- **Réseau : aucun.** Le conteneur est lancé avec `--network none`. Le gabarit autorise un seul port de la boucle locale de l'hôte (`127.0.0.1:${callbackPort}` pour un module, `127.0.0.1:${brokerPort}` pour un worker) : l'adaptateur ouvre, par sandbox, une socket Unix dans un dossier à elle, qui relaie vers ce port et vers lui seul, et monte ce dossier en lecture seule. Dans le conteneur, le même `127.0.0.1:<port>` relaie vers la socket : le module et le worker gardent les variables qu'ils ont sous srt. Un gabarit qui autorise autre chose qu'un port de la boucle locale est refusé. Mesuré avant de concevoir (`bench/docker-bridge`) : la requête passe, l'extérieur et la passerelle de l'hôte sont `ENETUNREACH`.
- **Fichiers.** Le conteneur ne voit que ce qu'on y monte : la racine de la plateforme en lecture seule, au même chemin que sur l'hôte (`${repo}` ne change pas, pas d'image à reconstruire à chaque version, pas d'écart entre le code de la gateway et celui des sandboxes), et des `tmpfs` pour son dossier de travail, sa configuration, son dossier temporaire et son dossier personnel, qui ne contient rien de l'hôte. Ni le dossier personnel de l'hôte, ni une autre sandbox. Ce système de fichiers est fixé par l'adaptateur : le gabarit donne le port et l'environnement, ses listes de chemins et de variables de l'hôte ne servent que sous srt. Un chemin qu'un montage ne peut pas porter (relatif, `/`, une virgule, un guillemet double, un caractère de contrôle) est refusé à la construction. Système de fichiers en lecture seule, aucune capacité, pas d'élévation, utilisateur non root, mémoire et nombre de processus bornés : les options déjà durcies de l'adaptateur.
- **Image.** Une image de l'exécutable `node` seul, désignée par la configuration avec son empreinte ; le code vient du montage. La socket de Docker n'est montée dans aucun conteneur. Amendé le 16 novembre 2026, après la première mesure de l'adaptateur réel devant un démon sans root (journal §54) : un lancement ne télécharge jamais (`--pull never`), l'image est déposée par l'opérateur, et son absence est un refus qui la nomme ; le point d'entrée que l'image déclare n'est pas exécuté (`--entrypoint`, le `node` de l'image, chemin absolu exigé) : celui de l'image officielle de node réécrit la commande qu'il ne connaît pas. La racine de la plateforme doit être lisible par les autres utilisateurs de l'hôte (l'utilisateur du conteneur n'est ni root ni l'opérateur) ; ses dossiers parents n'ont pas à l'être, le montage donne le dossier lui-même (mesuré).
- **Canari.** Au démarrage, un conteneur lancé avec ces options doit échouer à joindre une adresse et à écrire hors de ses `tmpfs` ; sinon `ISOLATION_UNAVAILABLE`, refus de démarrer. Construit (`DockerProcessRunner.check()`, journal §52) : `docker info` doit dire le démon sans root, puis un conteneur de contrôle, lancé par le même code qu'une sandbox, rapporte ce qu'il est et l'adaptateur juge : la valeur lue par le relais (le chemin d'un module vers l'hôte fonctionne pour l'utilisateur du conteneur), son uid, `lo` pour seule interface, `ENETUNREACH` vers l'extérieur, `EROFS` à l'écriture à la racine de l'image, dans la racine de la plateforme et dans le dossier du relais, une écriture réussie dans chaque `tmpfs`, et ses trois bornes. Un contrôle réussi n'est pas rejoué ; un refus n'est jamais retenu, le lancement suivant contrôle de nouveau. Le contrôle est celui de la plateforme, pas d'une sandbox : l'adaptateur est construit une fois, et les lanceurs qu'il rend pour chaque module et chaque tâche de worker (`withVariables`) le partagent. **Un refus dit sa cause** (un `docker info` arrêté par la borne du contrôle dit qu'il n'a pas répondu dans cette borne ; l'entrée du conteneur dit sur sa sortie d'erreur le signal qui a mis fin à son programme, ce qui est la seule trace d'un module tué à sa borne de mémoire) : la première condition qui manque, avec ce qui a été lu et ce qui était attendu ; et quand le conteneur de contrôle n'a rien imprimé (image absente, `node` introuvable à ce chemin, racine non compilée), ce qu'il a écrit sur sa sortie d'erreur, lue dans la même borne que son rapport. Un retrait du conteneur de contrôle qui ne peut pas être lancé fait échouer le contrôle (`COMMAND_NOT_FOUND`, le conteneur nommé), quoi que la sonde ait rapporté.
- **Configuration (construit, journal §53).** `GATEWAY_SANDBOX` vaut `srt` ou `docker`, sans valeur par défaut : absent ou autre, la gateway refuse de démarrer. Avec `docker`, cinq variables de plus, toutes requises, sans défaut : `GATEWAY_DOCKER_IMAGE` (avec son empreinte), `GATEWAY_DOCKER_NODE` (le chemin de `node` dans l'image), `GATEWAY_DOCKER_MEMORY_MIB`, `GATEWAY_DOCKER_PIDS`, `GATEWAY_DOCKER_CHECK_MS`. Avec `srt`, chacune doit être absente : ce qui est demandé et ne peut pas être donné est refusé, jamais ignoré. La configuration ne juge que la forme (un entier positif) ; les règles d'une option (empreinte, mémoire minimale) restent à un seul endroit, l'adaptateur, qui refuse avec ses mots. `platformSandboxes` (`packages/sandbox/src/platform-sandboxes.ts`) est le seul endroit qui transforme ce choix en lanceurs. Au démarrage, `serveNative` demande les sandboxes de la plateforme puis attend leur contrôle **avant de lancer quoi que ce soit** : un refus s'écrit sur la sortie d'erreur, code 1, aucun enfant, aucun port. Sous srt ce contrôle ne fait rien : srt prouve son confinement à chaque lancement, avec le gabarit de ce lancement. Un arrêt demandé pendant le démarrage attend la fin du démarrage, contrôle compris : sous Docker, la borne du contrôle s'ajoute donc au délai d'arrêt le plus long.
- **Arrêt.** Tuer le client Docker ne tue pas le conteneur (mesuré). À toute fin du client, qu'il finisse seul ou que `stop()` le tue, le relais est fermé d'abord (le conteneur perd son seul chemin vers l'hôte), puis le conteneur est retiré par son nom (`docker rm -f`) ; `exited` n'est résolu qu'ensuite. Amendé le 16 novembre 2026 : la première rédaction retirait le conteneur avant de fermer la socket.
- **Options ajoutées après revue** (journal §51, chacune mesurée devant un démon sans root). `--init` : l'entrée n'est pas le premier processus du conteneur, celui de Docker récolte les orphelins du programme, qui sinon restent zombies et comptent dans la borne de processus. `--log-driver none` : le démon ne garde aucune copie de ce qu'écrit le conteneur, dont le flux MCP d'un module. `--memory-swap` égal à `--memory` : pas de swap au-delà de la borne. Les bornes sont des nombres entiers, d'au moins 6 mébioctets pour la mémoire et 1 pour les processus (Docker lit 0 et -1 comme « sans borne »).
- **Ce qu'un gabarit ne peut pas demander.** Des fichiers à écrire, une variable du client Docker (`PATH`, `HOME`, préfixe `DOCKER_`) ou une variable que l'adaptateur pose lui-même : refus, jamais d'omission silencieuse. Les valeurs que pose le gabarit passent par nom (`--env NOM`), leur valeur dans l'environnement du client : une ligne de commande se lit par tout utilisateur de l'hôte, et l'une de ces valeurs est le jeton d'une task.
- **Arguments du programme (journal §55).** Les chemins que fixe l'adaptateur (`${repo}`, `${worktree}`, `${tmp}`, `${config}`, `${home}`, `${sandboxes}`) sont résolus dans les arguments du programme, comme sous srt : la topologie nomme le fichier d'un module `${repo}/…` (`topology/modules.mcp.json`). Les variables du lanceur ne le sont pas : l'une d'elles est le jeton d'une task, et une ligne de commande se lit par tout utilisateur de l'hôte ; le programme les reçoit par son environnement. Toute autre variable est refusée avant le contrôle et avant tout lancement. (Sous srt, toutes les variables sont encore résolues dans les arguments : même exposition, à fermer quand `srt-runner.ts` pourra être touché.) Trouvé en écrivant le bout en bout : sans cela, aucun module de la plateforme n'aurait démarré en conteneur, et aucun scénario devant le faux client ne le montrait, parce qu'aucun ne passait une commande de la topologie.
- **Sous-processus de l'agent (décision de mainteneur, journal §55).** Sous srt, le gabarit du worker demande à Claude Code de retirer le jeton de l'environnement de tout sous-processus et de l'isoler (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`), ce qui exige `bubblewrap`. Dans un conteneur de cet adaptateur, `bubblewrap` ne peut pas tourner : il lui faut un espace de noms utilisateur imbriqué, que le conteneur se voit refuser (aucune capacité, filtre d'appels système par défaut ; c'est l'attaque « makes a nested user namespace » du test d'évasion). Avec la valeur 1, le binaire de l'agent refuse de démarrer (mesuré en CI). Deux réponses étaient possibles : une image construite pour la plateforme, avec `bubblewrap`, où l'isolation ne servirait qu'à échouer ; ou dire dans le gabarit que cette protection dépend du moyen. Retenu : le gabarit porte `${subprocessScrub}`, que chaque moyen fournit (1 sous srt, 0 en conteneur), et l'image reste l'image officielle de `node`, désignée par son empreinte, sans rien à construire ni à publier. Ce qui est perdu en conteneur : un sous-processus lancé par l'agent verrait le jeton de la task. Ce qui le borne : le worker (node) lance le binaire de l'agent, et ce binaire ne lance rien : un profil de task ne peut lister que des outils MCP (`AgentFileSchema` refuse tout autre nom), le seul serveur MCP vit dans le processus du worker, aucun réglage ni hook n'est chargé (`settingSources: []`), et un appel de Bash, jamais offert, est refusé (sondé, journal §29) ; le conteneur ne tient qu'une task ; ce jeton ne vaut qu'au broker, pour cette task, et le conteneur ne joint rien d'autre. Dans le conteneur le jeton est déjà dans l'environnement du binaire et de node, sous le même uid : un sous-processus n'y ajouterait rien. De même, les refus d'écriture du gabarit (`.mcp.json`, `.claude` dans le dossier de travail) ne sont pas donnés en conteneur, où ce dossier est un `tmpfs` vide à chaque lancement : ils reposent sur ces mêmes options. Un profil de task qui recevrait un jour un outil lançant des commandes devrait rouvrir cette décision ; le schéma des profils est l'endroit qui l'interdit aujourd'hui.
- **Relais.** Chaque sens d'une connexion se termine pour lui-même : un client qui a fini sa demande lit encore sa réponse. Une erreur d'un côté détruit l'autre ; une simple fermeture, non (elle perdait la fin d'une réponse, `bench/docker-bridge/join.mjs`).
- **Hôtes.** Linux, et Windows par WSL2, avec Docker installé dans la distribution (l'intégration de Docker Desktop, où le démon tourne hors de la distribution, n'est pas mesurée). Sous macOS, Docker tourne dans une VM où une socket de l'hôte ne se monte pas, et srt y est supporté. srt reste le moyen privilégié partout où il tourne ; Docker est l'alternative.
- **Sans root, et seulement sans root.** Le démon Docker est celui du compte de la gateway (R-14). Devant un démon avec root, l'adaptateur refuse de démarrer (`ISOLATION_UNAVAILABLE`) : aucun champ de configuration ne l'autorise. Mesuré avant de concevoir (`bench/docker-bridge/rootless.sh`, journal §50) : le relais fonctionne ; l'utilisateur du conteneur tourne sur l'hôte sous un uid subordonné, lit la racine montée et ne peut pas y écrire ; les bornes de mémoire et de processus s'appliquent sous cgroup v2 délégué.
- **AppArmor.** La documentation de Docker range AppArmor parmi ce que le mode sans root ne supporte pas, et sur un hôte où AppArmor est actif le démon refuse de lancer un conteneur sans `--security-opt apparmor=unconfined` (mesuré). L'adaptateur passe donc cette option : dans ce mode il n'y a pas de profil à perdre. Ce qui confine le conteneur : l'espace de noms utilisateur (uid subordonné sans privilège), le filtre d'appels système par défaut de Docker, aucune capacité, pas d'élévation, système de fichiers en lecture seule, aucun réseau.
- **Canari, complété.** Sur un hôte où les bornes sont ignorées (cgroup v2 non délégué), refus de démarrer. Amendé le 16 novembre 2026 : la première rédaction voulait que le conteneur de contrôle soit tué par sa borne de mémoire et voie ses processus refusés. Il lit à la place les fichiers de son propre cgroup (`memory.max`, `memory.swap.max`, `pids.max`), qui sont ce que le noyau applique : ils valent la borne demandée quand elle est posée, `max` sinon (mesuré, `bench/docker-bridge/canary.sh`). Faire tuer un conteneur à chaque démarrage demanderait d'allouer au-delà d'une borne de plusieurs centaines de mébioctets sur l'hôte ; que la borne posée tue bien est mesuré une fois, hors production (`rootless.sh`, `lifecycle.sh`). La borne de mémoire se donne en mébioctets, au moins 6 : le noyau arrondit une borne à la page, et Docker refuse moins de 6 Mo (mesurés).
- **Ce que la gateway ne fait pas.** Elle ne télécharge pas l'image (un lancement la trouve sur place ou est refusé), et elle ne démarre ni ne règle le démon : c'est le travail de l'opérateur (sans pont ni NAT, `--bridge=none --iptables=false --ip6tables=false`, puisqu'aucun conteneur n'a de réseau ; documentation de déploiement, 1b.6d). Podman n'est pas supporté : un seul moteur, prouvé.

| STRIDE | Menace propre à ce mode | Réponse |
| ------ | ----------------------- | ------- |
| **S** | Un conteneur se dit d'une autre task | Inchangé : identifiant d'appel pour un module, jeton de task pour un worker (§2) |
| **T** | Image remplacée ; code de la plateforme modifié depuis le conteneur | Image désignée par son empreinte ; racine montée en lecture seule, système de fichiers en lecture seule |
| **R** | Appel non attribuable | Inchangé : la gateway journalise, le broker rend l'usage par jeton |
| **I** | Lecture de l'hôte, sortie vers l'extérieur, autre conteneur | Aucun réseau ; un seul port relayé ; rien de l'hôte monté hors de la racine de la plateforme et de la socket du relais |
| **I** | Jeton de la task lu par un sous-processus de l'agent, que `bubblewrap` ne peut pas isoler dans un conteneur | Risque accepté et borné (« Sous-processus de l'agent ») : le worker n'a aucun outil qui lance un processus ; un conteneur ne tient qu'une task ; le jeton ne vaut qu'au broker, seul port joignable, pour cette task |
| **D** | Conteneur qui ne finit pas, qui épuise l'hôte | Mémoire et processus bornés par Docker (srt ne les borne pas) ; arrêt par `docker rm -f` ; borne de l'arrêt de la gateway (§8, 1b.6a) |
| **E** | Sortie du conteneur vers l'hôte ; la gateway comme chemin vers root | Démon sans root seulement : ni le démon ni le conteneur n'ont un privilège de l'hôte ; aucune capacité, pas d'élévation, non root dans le conteneur, socket Docker jamais montée. Pas de profil AppArmor dans ce mode (limite documentée de Docker) |

**srt non supporté** : ni macOS avec `sandbox-exec`, ni Linux x64/arm64 avec `bwrap`, `socat`, `ripgrep` et des espaces de noms utilisateur ; `kernel.apparmor_restrict_unprivileged_userns=1` sans profil AppArmor ; conteneur sans espaces de noms utilisateur [E-07] ; root sans `CAP_SETFCAP`.

**Canari, léger.** Au démarrage, une sandbox doit échouer à lire un fichier hors `allowRead` et à joindre une adresse hors allowlist. Tout autre résultat : `ISOLATION_UNAVAILABLE`, refus de démarrer, aucun repli (prouvé : `features/sandbox/canary.feature`, brique 1b.1).

**Montée de srt.** Le banc se rejoue à chaque montée de version et le rapport se compare au précédent, dans les deux sens, par OS (T-54). Un test d'évasion réussi que srt ne corrige pas, ou un abandon de srt, rouvre le choix : options et test de pérennité au journal.

## 7. Porte de CI

Seul le résultat des tests fait foi : aucun hash, aucun digest. **Trois familles** : e2e Gherkin (`features/**`, srt et Postgres réels), unitaires Gherkin (`<composant>/features/**`), mutation Stryker. Typecheck, format et garde d'architecture sont des scénarios ; la validation des plugins distribués relève de la brique 1c (le dernier plugin, `builder-guard`, et son scénario sont partis avec la décision 2, `000a540e`). Outils : `@cucumber/cucumber` 12.9.0, `@stryker-mutator/*` 10.1.1, `tsx` [T-13, T-14].

**Le compte.** `exécutés = base + ajoutés − supprimés`.

1. L'unité est le pickle : un `Scenario`, une ligne d'`Examples`, un `Scenario` de `Rule` [T-12].
2. `base` = compte de pickles exécutés, publié en artefact par chaque job (`gate-base-linux`, `gate-base-macos`) et lu, par l'API (`actions: read`), dans le run vert de `gate.yml` sur `main` qui porte le SHA du premier parent. Repli écrit : si aucun run vert de `main` ne porte le SHA du premier parent du commit de merge, la base est le compte statique du premier parent et la porte le signale dans son rapport au lieu d'être rouge ; le premier run de `main` et l'artefact expiré tombent dans ce repli. `ajoutés` et `supprimés` = différence d'ensembles entre ce premier parent et la tête, dérivée du diff, jamais déclarée. L'identité d'un pickle : chemin, `Feature`, `Rule`, `Scenario`, ligne d'`Examples`.
3. La porte est verte si et seulement si tous les pickles attendus sont exécutés, verts, une seule tentative, chaque step `PASSED`. Elle lit le rapport Messages, jamais `TestRunFinished.success` : un step `SKIPPED` y donne `success: true` et un code de sortie 0 [T-13c]. `cucumber.mjs` n'a ni `tags` ni `name`, `retry: 0` ; une table `Examples` calculée est interdite.

Hors repli, la base venant d'une exécution réelle, `exécutés = base + ajoutés − supprimés` est un contrôle réel, et `exécutés = statique` reste : ensemble, ils attrapent filtres, skips, steps absents et un compte statique faussé par la PR ; le résumé `+a −s` rend toute suppression visible à la revue.

**Mutation.** 0 survivant sur le périmètre, sources de production : les lignes modifiées du diff, que `test-gate plan` passe à Stryker en plages (`fichier:début-fin`, une par suite de lignes consécutives : Stryker ne génère que les mutants contenus dans une plage) ; un fichier dont une entrée de dette est retirée, et le canari, sont mutés en entier ; seul le run hebdomadaire mute tout le code, hors la dette connue du registre `tools/test-gate/mutation-debt.json` (règle 6, plus bas, qui ne peut que rétrécir). `Survived`, `NoCoverage`, `Pending` échouent ; `CompileError`, mutant que l'outil n'a pas su compiler, échoue aussi ; `Killed`, `Timeout` et `RuntimeError` passent si le rejeu de la règle 7 les confirme. Un équivalent se marque `// Stryker disable next-line <Mutateur>: équivalent: <invariant>` : la porte juge la forme, la revue l'équivalence. Du code exécuté seulement dans un processus enfant survit [T-14b] : d'où les ports avec adaptateur en mémoire, déjà la règle du dépôt. Coût mesuré : 46 à 75 ms par mutant [M-01]. Stryker tourne avec un seul worker : la suite n'est pas faite pour le parallélisme, et des workers qui partagent le répertoire et les ports rendent le statut d'un mutant non reproductible. Un test modifié n'étend pas le périmètre : ce qu'il cesse de tuer est vu par le run complet `.github/workflows/mutation-full.yml`, planifié, hors du chemin d'une PR, rouge si les survivants diffèrent du registre (risque accepté par le propriétaire le 2 novembre 2026).

Les commandes `test-gate inventory --job linux` et `test-gate inventory-check --job linux` produisent puis vérifient un inventaire de lots par fichier. L’inventaire énumère les mutations natives avant de les projeter sur les lignes touchées. Le contrôle régénère le manifeste, compare ses octets et rapproche le rapport en périmètre fichier entier des lots attendus, y compris les empreintes des sources et les motifs d’ignorance natifs. En CI Linux, des producteurs isolés reçoivent des tranches disjointes de l'inventaire et chacun joue le canari (paragraphe suivant). La commande inventory-project vérifie le rapport brut puis écarte uniquement les lignes de comptabilité hors lot. Les runners de rejeu et le collecteur vérifient chaque rapport natif et son catalogue Cucumber avant de les agréger. Ils préservent le canari de chaque producteur et qualifient les identifiants propres à chaque invocation. Le collecteur exige un reçu de rejeu de chaque lot, lié au SHA-256 du rapport agrégé. La porte locale (`npm run gate`, `inventory --job linux`, `inventory-check`) n'utilise pas ce plan : elle lance un seul Stryker sur l'inventaire entier, sélectionne les fichiers entiers, puis compare les identités des mutants qui rencontrent une ligne changée à son inventaire natif. La sélection réduite des scénarios statiques reste à établir.

**Lots hébergés : le plan suit le travail, et le juge le re-dérive.** Jusqu'au 26 novembre 2026 le nombre de lots était une constante, seize. Mesuré sur six runs (45739094567, 45744632805, 45743125948, 45767197864, 45770810106, 45771449037 ; 96 lots) : chaque lot commence par un essai à blanc de toute la suite, 265,5 s en médiane (235 à 451 s) ; un lot coûte environ 6,6 minutes de job avant son premier mutant (job de mutation 5,3, job de rejeu 1,3). Sur les trois runs dont le périmètre était vide, seize lots ont joué le seul canari : environ 105 des 125 minutes de job du run. Avec 84 mutants (45771449037), 81 minutes d'essais à blanc pour 12 minutes de mutation, et un lot à 267 s de mutation contre 1 s pour trois autres : le coût estimé ignorait les mutants statiques, qui rejouent chacun toute la suite. Ce qui change :

1. *Le plan.* `tools/test-gate/src/infrastructure/hosted-lots.ts` estime le coût de chaque mutant actif (échantillon mesuré de `tools/test-gate/hosted-mutation-cost.json`, sinon repli du fichier, sinon repli global), sauf un mutant qu'aucun corps de fonction du lot n'entoure (ni mutant `BlockStatement` ni mutant `ArrowFunction` ne le contient) : sans échantillon mesuré, il est tenu pour statique et coûte un passage de la suite (`suiteRunMs`). C'est une estimation : un mutant d'une fonction appelée au chargement du module reste sous-estimé, un initialiseur de propriété de classe est surestimé. Le nombre de lots est `max(1, min(maxLanes, ⌊coût total / laneTargetMs⌋))` : un lot ne s'ouvre que si la mutation qu'il retire aux autres vaut au moins l'essai à blanc qu'il ajoute. Un lot resté sans mutant de production après la répartition n'est pas ouvert. Un périmètre vide donne un lot, celui du canari. `suiteRunMs`, `laneTargetMs` (la médiane mesurée de l'essai à blanc) et `maxLanes` vivent dans `tools/test-gate/hosted-lanes.json` avec leur provenance ; `maxLanes` vaut 16 : seize lots de mutation, deux lots Cucumber et le job macOS font dix-neuf jobs simultanés, sous le plafond de vingt du plus petit forfait de GitHub.
2. *Qui démarre quoi.* Un job `gate-linux-plan` calcule le plan (`hosted.ts lanes`) et publie la liste des lots ; la matrice de `gate-linux-lane` est cette liste. Chaque lot fait mutation puis rejeu, comme avant, et re-dérive lui-même sa tranche. La sortie du job de plan ne décide que de ce qui démarre.
3. *Qui juge.* `gate-linux` re-dérive le plan depuis son propre checkout (`hosted.ts lanes`, même planificateur, mêmes entrées), ne télécharge que les producteurs de ce plan, refuse tout job ou artefact de lot hors du plan, et exige de `hosted.ts collect` exactement ces reçus : le manifeste de chaque lot, octet pour octet, porte la tête, le premier parent, la destination, le numéro du lot et sa tranche ; le reçu de rejeu porte l'empreinte de ce manifeste et celle du producteur. La liste annoncée par le job de plan est comparée à la liste re-dérivée : plus courte, plus longue ou absente, la porte est rouge. Un job de plan en échec ou annulé laisse la matrice sans départ : l'étape d'admission de `gate-linux`, qui tourne toujours (`always()`), est rouge. Les contrôles requis du ruleset restent `gate-linux` et `gate-macos` ; aucun nom de lot n'est requis.

Ce qui ne change pas. La règle 5 juge le même ensemble de mutants : le plan ne décide que de la répartition, et le collecteur exige toujours que le rapport agrégé contienne l'inventaire entier, chaque identité une fois (`requireCompleteMutationLots`), le canari une fois par producteur. La règle 7 garde sa liaison : le canari est joué par chaque Stryker qui tourne, donc dans chaque lot, et au moins un lot tourne toujours ; un rapport de lot dont le canari manque ou ment n'est pas lu ; chaque verdict d'un lot est rejoué par le job de rejeu de ce lot, sur un autre runner. Le déterminisme tient aux entrées : l'arbre du commit jugé, son premier parent, les deux fichiers descriptifs de cet arbre ; ni horloge ni environnement ; les fichiers en ordre lexical, les groupes triés par profondeur puis coût, les égalités dans l'ordre de l'inventaire. Aucun cache, aucune action, aucune permission, aucune dépendance de plus.

Menaces (STRIDE) du reçu d'un lot. Qui l'écrit : le job du lot, qui exécute le code de la PR. *Usurpation et falsification* : un lot ne peut pas se déclarer hors plan ni changer sa tranche, le juge compare son manifeste à celui qu'il re-dérive ; un reçu d'une autre tête ou d'un autre plan n'a pas les mêmes octets. *Répudiation* : le fichier `producer` nomme le run, la tête, la tentative, le job et l'artefact d'origine. *Déni de service* : un plan gonflé est borné par `maxLanes`, et refusé par le juge s'il diffère du sien. *Élévation* : aucune permission ne change. Limite, dite telle qu'elle est : le workflow, `tools/test-gate` et ses fichiers descriptifs sont dans l'arbre jugé ; une PR qui les réécrit change la porte qui la juge, hier comme aujourd'hui. Ce que la re-dérivation garantit est plus étroit : à code de porte donné, ni un lot ni la sortie du job de plan ne retirent un mutant du jugement. Réécrire la porte relève de la revue (R-6), et le run de `main` rejoue le commit avec la porte fusionnée.

La livraison (`tools/deliver`) lit toujours le verdict de `gate-linux` ; pour distinguer un run sans runner d'un run rouge, elle prend les lots du run par leur famille de noms (`plannedProducers` de `deliver.json`), pas par une liste fixe, et ne re-dérive pas le plan : sur un commit en avance de plusieurs commits, le premier parent de la porte locale (la destination) n'est pas celui du run hébergé (`HEAD^1`), et un second plan divergerait du premier. Restent à établir par un run hébergé : la durée réelle du job de plan en série, la durée d'un run seul et sous contention.

**Contrôle de l'outil de mutation (règle 7).** La porte ne croit pas Stryker sur parole : elle vérifie chacun de ses verdicts hors de lui. Deux contrôles, déclarés dans `gate.json` (`canary`, `replay`), lus par `check` avant toute conclusion. **Canari** : `tools/test-gate/canary/canary.ts` est muté à chaque run avec mutation ; tout mutant de `sum` et `greet` (assertés par `tools/test-gate/features/canary.feature`) doit être `Killed`, de `twice` (exécuté sans assertion) `Survived`, de `thrice` (jamais atteint) `NoCoverage`. Un seul statut faux, ou un mutant hors des fonctions déclarées, et la porte est rouge. Le canari n'est pas de la production : ni la règle 5 ni le registre de la règle 6 ne le lisent. **Rejeu** : `test-gate replay`, entre Stryker et `check`, écrit chaque mutant du périmètre et du canari dans l'arbre et lance lui-même `cucumber-js --profile replay <feature>:<ligne>…` sans le runner ni l'instrumentation de Stryker, puis réécrit le fichier. Un run est un passage propre si chaque scénario attendu a tourné une fois, chaque step et chaque hook de run en `PASSED`, avant sa limite. **Détection** (`Killed`, `Timeout`, `RuntimeError`, que le runner Cucumber de Stryker donne à un step qui lève autre chose qu'une assertion) : les scénarios passent proprement sur le code original (témoin : une commande de test cassée ne confirme jamais rien) et pas sur le mutant, par un step en échec, un plantage sans rapport ou un run au-delà de sa limite. Une détection qui ne repose pas sur un step `FAILED` (pas de rapport, limite, hook, scénario manquant, step ni passé ni en échec) ne tient que si un nouveau témoin, lancé juste après, passe proprement : un environnement cassé ne confirme aucun mutant. Stryker ne nomme que le premier tueur qu'il voit : si les tueurs nommés d'un `Killed` passent, ses scénarios couvrants décident. **Survie** (`Survived`, `Ignored`) : les scénarios couvrants, ou toute la suite du rapport pour une équivalence revendiquée et pour un mutant statique, passent proprement sur le mutant. Tout run avec témoin est borné à trois fois la durée du témoin plus dix secondes, les autres à `replay.limitMs`. Chaque run est chef de son groupe de processus, tué en entier à sa fin : les processus lancés par ses scénarios ne lui survivent pas. Toute contradiction est rouge ; le rejeu est lié au rapport par le SHA-256 de son texte, et un fichier qui diffère du rapport n'est jamais muté. Une PR rejoue son périmètre ; `.github/workflows/mutation-full.yml` rejoue chaque mutant chaque semaine (`replay --all`). Limite : un mutant `NoCoverage` n'est pas rejoué, aucun scénario n'étant nommé ; son statut est déjà rouge ou au registre, et le canari prouve que l'outil sait le reconnaître.

**Dette de mutation (règle 6).** La porte reste stricte ; les survivants du code antérieur à la brique sont une dette connue, inscrite en clair dans `tools/test-gate/mutation-debt.json` (chemin : clé `debt` de `gate.json`). Une entrée : fichier, positions de début et de fin du rapport Stryker (lignes et colonnes depuis 1, fin exclue), mutateur, code remplacé (`original`) et `replacement`. Son identité est le texte `fichier:l:c-l:c mutateur original -> replacement`, jamais l'`id` du mutant. Un mutant `Survived` ou `NoCoverage` du périmètre qui figure au registre est accepté et compté ; `Pending` reste rouge. Le registre ne peut que rétrécir, et ce compte ne dépend pas des positions : pour chaque (fichier, mutateur, `original`, `replacement`), le registre ne tient pas plus d'entrées que celui du premier parent (lu par `git show`) ; une entrée en plus est rouge, une entrée replacée ne l'est pas ; un premier parent sans registre autorise la création, et le rapport le dit. Retirer une entrée dont le fichier existe encore exige la preuve de Stryker : le fichier entre dans la liste à muter, et le retrait est rouge si le fichier n'est pas dans le rapport ou si le survivant existe toujours ; retirer une dette payée, ou dont le fichier a disparu, est permis. Une entrée dont le fichier a disparu, ou dont le fichier est dans le rapport sans aucun mutant de même identité (quel que soit son statut), est rouge : « introuvable (code supprimé ou déplacé) », à retirer dans la même PR. Une entrée dont le mutant existe mais n'a pas survécu à ce run (`Killed`, `Timeout`, `RuntimeError`, `CompileError`, `Ignored`) n'est pas rouge : elle est comptée dans le rapport (« entrées dont le mutant n'a pas survécu à ce run »), à retirer du registre quand la dette est payée ; un mutant `Pending`, `NoCoverage` ou `Survived` reste « rencontré ». Une entrée dont le fichier n'est pas dans le rapport n'est pas jugée. Limite : les survivants de Stryker varient d'un run à l'autre (environ 19 mutants sur 750 changent de statut entre deux runs complets sur macOS, et le run Linux de CI en ajoute d'autres) ; le registre est donc l'union de plusieurs runs complets (macOS et Linux). Un survivant qui n'a été vu dans aucun de ces runs rend la porte rouge (règle 5) ; il se tue par un scénario, il n'entre pas au registre. Une entrée doit toujours désigner son texte : le code du fichier entre son début et sa fin est son `original`, vérifié à chaque passage sans dépendre de ce que le run a muté ; sinon elle est rouge, « désalignée (le code a bougé) », et par ce seul contrôle. Jusqu'au 16 novembre 2026 un décalage de lignes dans un fichier à dette laissait l'entrée désigner autre chose sans que rien le dise, tant que ces lignes n'étaient pas mutées : 114 entrées sur 295 étaient dans cet état (journal §35, §60, §66). `test-gate debt realign` replace les entrées dont le code a seulement bougé, sans jamais en ajouter ni en retirer. Il ne devine pas : une entrée dont le texte se trouve à une seule place libre, aux mêmes colonnes, y va, sauf si une autre entrée de même sorte n'a que cette place, auquel cas aucune des deux ne bouge ; quand le texte se trouve à plusieurs places, elle ne bouge que vers celle que désigne l'écart de sa voisine alignée ou replacée la plus proche, au-dessus ou au-dessous, un déplacement de lignes décalant un bloc d'un même écart ; deux places désignées, aucune, ou une place désignée pour deux entrées, et elle ne bouge pas : la commande la nomme et sort en 1, et le mainteneur tranche par une mutation du fichier. `test-gate debt` écrit le registre une fois, depuis le rapport de mutation, et refuse s'il existe.

**Où.** Deux fichiers d'entrée aux jobs identiques : `gate.yml` (nom `gate`), sur `pull_request` seul (jamais `pull_request_target`), et `gate-push.yml` (nom `gate-push`), sur `push` vers `main` et vers les branches d'essai de la livraison (`sentinel/gate-1a-*`, où un commit reçoit ses deux contrôles avant d'atteindre `feat/gate-1a` puis `main` ; journal §80), runners hébergés, `contents: read` et `actions: read`, aucun secret, aucun cache, `fetch-depth: 2`, puis la destination de la porte (`refs/remotes/origin/main`, clé `destination` de `gate.json`) pointée sur le premier parent du commit jugé, jamais récupérée de la branche vivante, qui a pu bouger depuis ; la porte locale, sur une branche de plusieurs commits ou qui a intégré `main`, juge toute la branche contre elle (`tools/test-gate/src/domain/destination.ts`). `gate-linux` valide deux rapports Cucumber issus de runners isolés et les rapports de mutation liés à leur rejeu. Les deux lots fonctionnels et les couloirs de mutation démarrent en parallèle : 36 jobs par run aujourd'hui (2 lots Cucumber, 16 jobs de mutation, 16 rejeux, 2 jobs de verdict), sur une limite de jobs simultanés que tous les runs du compte partagent. Mesuré sur les runs de `gate.yml` du 21 au 26 novembre 2026 (UTC), alors seule entrée et sans groupe : sur l'échantillon d'origine, les 100 dernières lignes de l'API moins 8 annulations, soit 92 runs, médiane de 8,6 minutes pour un run seul et de 54,0 minutes avec dix runs qui le chevauchent ; sur la fenêtre entière, paginée, 145 runs terminés non annulés et 59 paires de runs qui se chevauchent sur la même branche de pull request. Les runs d'une même pull request partagent donc un groupe de concurrence, écrit littéralement au niveau du workflow dans `gate.yml` (`group: gate-pr-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`) : un nouveau commit annule le run du commit qu'il remplace, et le seul déclencheur étant `pull_request`, le numéro existe toujours. `gate-push.yml` ne déclare aucune clé `concurrency`, ni au niveau du workflow ni sur un job, et `gate-lane.yml` non plus : `cancel-in-progress: false` ne protège pas un run d'un run ultérieur qui nomme son groupe, un groupe ne peut pas être vide et `concurrency` ne s'omet pas sous condition, alors qu'un run sans groupe ne peut pas être annulé par ce moyen. Sont ainsi hors de tout groupe le run de `main`, qui publie la base du compte, et celui d'une branche d'essai, que la livraison attend (`workflow: gate-push` dans `tools/deliver/deliver.json`). Les deux jobs de verdict cherchent la base dans le run vert de `gate-push.yml` sur `main` pour le premier parent : tant que `main` n'en a pas, la porte prend le repli écrit du point 2 (compte statique du premier parent, signalé) : ce sont les runs de la pull request ou de la branche d'essai qui apporte ce changement, puis le premier push sur `main`, dont le premier parent a été jugé par `gate.yml`. De la ligne `jobs:` à la fin, les deux fichiers sont les mêmes octets : le ruleset de `main` exige les contextes `gate-linux` et `gate-macos`, un contrôle requis ne tient compte ni du workflow ni de l'événement, et un job d'un workflow appelé se rapporte sous `<job appelant> / <job>` (GitHub, « Troubleshooting rules ») ; les deux jobs de verdict restent donc des jobs de chaque entrée. `pipeline-after-merge.yml` lit le run `pull_request` du fichier `gate.yml`, de nom `gate` : il n'est pas modifié. La règle est tenue par `features/descriptive/gate-concurrency.feature`, qui compare des valeurs littérales, n'évalue aucune expression, et lit tous les fichiers `.yml` et `.yaml` de `.github/workflows`, au niveau du workflow et de chaque job, pour qu'aucun autre ne nomme un groupe commençant par `gate-` ; elle ne voit pas un groupe qu'un autre workflow calculerait à l'exécution, lequel ne pourrait annuler qu'un run de pull request. Une annulation n'a pas un seul effet sur les jobs : dans les 22 runs annulés du 21 au 26 novembre 2026, `gate-linux` a échoué à « Require all producers » à chaque fois, `gate-macos` a réussi 20 fois et a été annulé 2 fois ; le run annulé 45162457452 de `main` a gardé `gate-base-macos`, que le filtre `status=success` de la recherche rend inéligible. Un ruleset accepte `success`, `skipped` et `neutral`, et bloque sur un échec, une annulation ou un résultat manquant. Un second push rapproché, ou la relance d'un ancien run, peut annuler le run de la tête courante d'une pull request : l'échec est fermé, la tête n'a pas de vert tant que son run n'est pas relancé, et un vert n'est jamais reporté sur un autre SHA. Défaut ouvert, à la charge de la refonte de la livraison : `GhForge.run` (`tools/deliver/src/infrastructure/gh-forge.ts:86`) prend le plus petit identifiant de run qui correspond au nom affiché du workflow et au SHA de tête, quels que soient l'événement et la branche. Avant ce changement, un run de pull request réussi pour une tête H, qui jugeait un commit de fusion synthétique et non H, pouvait passer le premier, et `deliver --until ci` pouvait rendre `ready` alors que le push d'essai de H était en attente ou en échec ; la relance de cet ancien run pouvait aussi annuler la tête courante. Avec deux noms affichés, un run `gate` ne correspond plus à `workflow: gate-push` ; la sélection n'est toujours pas liée à l'événement `push`, à la branche d'essai et au SHA ensemble : un run `gate-push` du même SHA sur `main` ou sur une autre branche d'essai correspond encore. Non prouvé avant un premier run hébergé de ces deux fichiers : qu'une pull request rapporte exactement `gate-linux` et `gate-macos` depuis `gate.yml` ; qu'un nouveau push sur une pull request annule le run du commit remplacé ; qu'un push sur `main` lance `gate-push.yml` hors de tout groupe et publie `gate-base-linux` et `gate-base-macos`, et que le run suivant les trouve ; et que le repli décrit plus haut s'arrête à ce premier push sur `main`. Une relance partielle peut reprendre le rapport d’un producteur vert de la même exécution et du même SHA. `gate-macos` lance `features/sandbox/` seulement, parce que srt y diffère réellement [T-02e, T-07-fd0, T-39b] et que le reste n'en dépend pas. Un ruleset protège `main`, les deux jobs requis, avec droit de contournement du propriétaire ; il ne protège pas les refs locales (§8, 1a.0). Ni `CODEOWNERS` ni purge des 474 mutants. `CLAUDE.md` s'amende en 1a pour permettre le diff des `.feature` contre le premier parent. Une commande locale : `npm run gate`.

Le code de la porte vit dans l'arbre testé (`tools/test-gate`) : un commit qui le casse échoue à sa propre porte, et il n'y a rien à promouvoir. Il se teste avec des rapports fixtures : step non défini, step `pending`, filtre, scénario sans step, pickle absent, base d'un autre SHA, mutant survivant, `Stryker disable all`. Toute manipulation délibérée relève de R-6.

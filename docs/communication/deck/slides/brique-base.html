Si vous ne retenez qu’une chose pratique, c’est celle-ci. La brique de base tient en une commande, lancée depuis votre worktree : npm, tiret tiret prefix, le dossier du lanceur, run code. Elle lance le proxy d’authentification de l’hôte, puis votre Claude Code habituel, mais à l’intérieur d’un sandbox, sous srt, dans votre worktree habituel. Le profil builder.json, résolu à chaque lancement et écrit hors de tout chemin inscriptible, dit ce qui est permis. Écrire : le worktree, et les parties de git nécessaires à un commit. Refusé : les hooks git, la configuration git commune, les fichiers de réglages Claude Code du worktree, qu’une session Claude Code de l’hôte ouverte dans ce worktree lirait (R-2), et le fichier de réglages de la session, qui porte les règles de refus permissions.deny ; depuis le 4 novembre 2026, ces règles remplacent les hooks de protection, que Claude Code en mode --bare n’exécute pas (décision 2). Illisibles : ~/.ssh, ~/.aws, ~/.gnupg et les autres dossiers d’identifiants. Réseau : le proxy d’authentification de l’hôte, seul chemin vers Anthropic, et le registre npm, rien d’autre ; ni GitHub ni l’API en direct, et aucun jeton GitHub : fetch et push se font depuis l’hôte. Les risques qui restent sont écrits, R-1 et R-2, par exemple le jeton de session, lisible dans la sandbox pendant la session ; le trousseau, lui, est illisible. C’est aussi le stage 0 : le reste de la plateforme se construit à l’intérieur de cet outil. Ce qui est vérifié : sur le poste macOS, la commande fonctionne en mode non interactif avec le compte Claude, sur un appel réel minimal. L’interface interactive, la TUI, est prouvée en pty, un pseudo-terminal ; son premier lancement réel revient au propriétaire. Une première version du profil avait d’ailleurs permis une évasion, prouvée en réécrivant un pointeur de worktree ; c’est ce qui a conduit aux refus que vous voyez ici.

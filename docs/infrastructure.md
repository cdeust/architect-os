# Infrastructure

How the platform runs on a host, what it needs and what it refuses: [operating.md](operating.md). An example of an edge in front of its loopback port: `deploy/edge/Caddyfile`; nothing in this tree starts it.

## Secrets broker

Rule: no secret ever enters a worker. The worker is given `ANTHROPIC_BASE_URL` pointing at the broker and a task token as its API key. `modules/broker` (brick 1b.2, `docs/design/platform-v3-srt.md` §2) is that broker: one listener on `127.0.0.1`, port fixed in `modules/broker/broker.json`; the API key in a file only its owner reads (0600, refused otherwise, at start and at each request); task tokens granted and revoked by the gateway with the MCP tools `token_grant` and `token_revoke` on the broker's stdio; only `POST /v1/messages` (and `count_tokens`) to `api.anthropic.com`, the key in `x-api-key`, the body unchanged and admitted by the request policy of 1a.0; one usage record per answer (task, parent, model, tokens, never content) sent to the gateway as `notifications/message`, logger `usage`. Not yet launched by the gateway (brick 1b.4): `compose.yaml` still wires `BROKER_URL`, and workers in compose cannot call Anthropic; tests use a scripted agent. The real call of the broker (T-04R) is `.github/workflows/broker-live.yml`, run on `main` only (push touching the broker, weekly schedule, manual dispatch; never a pull request): `gate.yml` holds no secret, and neither does this workflow. It asks GitHub for the identity token of its run and exchanges it at Anthropic for an access token of a few minutes (workload identity federation), which it writes to a 0600 file of the runner, gives to `npm run broker:live` as a bearer, and removes. The owner created, once, in the Claude Console: an issuer for GitHub Actions, a service account in a workspace with a low spend limit, and a rule that accepts the token of this repository only. That rule pins the subject of a run on `refs/heads/main` in GitHub's immutable form (`repo:<owner>@<owner id>/<repository>@<repository id>:ref:refs/heads/main`, which this repository emits), the repository and its owner by name and by number, the reference, and the `workflow_ref` claim to `broker-live.yml` on `main`. The last one matters: the two workflows of the Claude Code action also ask for an identity token, and one of them runs in the context of `main`, with the same subject. The four identifiers of the rule (organisation, service account, rule, workspace) are repository variables, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID`, `ANTHROPIC_FEDERATION_RULE_ID` and `ANTHROPIC_WORKSPACE_ID`: they are not secrets, and without one of them the workflow fails at its exchange step and says so. The job names no GitHub environment, since an environment would change the subject of the token; the environment `broker-live` that GitHub created on 17 November 2026 is unused. `features/descriptive/workflows.feature` refuses any copy of the workflow that widens its triggers or permissions, names an environment, stores a secret or traces its commands, any other workflow that exchanges an identity token at Anthropic, and any workflow outside a closed list that asks GitHub for one. Locally, the same run is `ANTHROPIC_TEST_KEY_FILE=<0600 file> npm run broker:live` with a test key of the owner. Other secrets: `GATEWAY_TOKENS` (local development only, token table adapter) and `POSTGRES_PASSWORD` come from the git-ignored local env file or the platform secret store; only `data` and `postgres` receive the database password.

## Postgres, pgvector and migrations

- Postgres 17 with the `vector` extension (the CI job `gate-linux` runs `pgvector/pgvector:pg17`).
- `data/migrations/<NNNN>_<name>.sql`, applied in order, once each, inside a transaction, recorded in `schema_migrations` (`data/src/infrastructure/migrate.ts`). The `data` service applies pending migrations at start.
  - `0001_runs.sql`: registry of executions (`runs`, `run_events`).
  - `0002_memory.sql`: `CREATE EXTENSION vector`, schema `memory`, table `memory.memories` with `embedding vector(384)` and an HNSW cosine index. The dimension must equal `EMBEDDING_DIMENSION` in `packages/contracts/src/data-ops.ts`, which rejects any other length at the API.
  - `0003_runs_immutable.sql`: a trigger refuses any update of a completed run (SQLSTATE 55000, reported as `INVALID_OPERATION`).
- Never edit an applied migration: add a new numbered file.
- Operations: `data/sql/<op>.sql`, listed in `data/sql/operations.json` with their parameters (the SQL of each writes exactly the tables its operation declares in `DATA_OPS.writes`), the SQLSTATEs that mean a named failure (23503 unknown run: `NOT_FOUND`; 55000: `INVALID_OPERATION`) and the shape of the answer. The data image ships `sql/` and `migrations/` (the root Dockerfile copies `data/`).
- Without `DATABASE_URL`, `data` starts with the in-memory store (non-persistent, development only).

## CI

`.github/workflows/gate.yml`: the CI gate (`npm run gate`, docs/design/platform-v3-srt.md §7) on pull requests, on pushes to `main` and on the trial branches of the delivery (`sentinel/gate-1a-*`), in two jobs, `gate-linux` (the whole suite, with Postgres) and `gate-macos` (`features/sandbox/` only), with `contents: read` and `actions: read`. The design has a ruleset on `main` require both (docs/design/platform-v3-srt.md, decision 4); it is a setting of the repository, decided by its owner. Since 17 November 2026 the ruleset of `docs/design/ruleset-main.json` is active on `main`, and the same on `feat/gate-1a`, where the maintainer's commits land first (no deletion, no rewrite, both jobs required, the owner's role may bypass); the second is created from that file with its name and its branch replaced (`jq '.name="feat/gate-1a" | .conditions.ref_name.include=["refs/heads/feat/gate-1a"]' docs/design/ruleset-main.json | gh api repos/<owner>/<repo>/rulesets -X POST --input -`). It was put on the branch first and replicated on `main` once the delivery was seen to satisfy it without the bypass (journal §75, §76). The account that delivers has the owner's role: the ruleset records each push, it does not stop that account. Typecheck, format and the architecture guard are scenarios of the suite. `claude.yml` is copied from an `anthropics/claude-code-action` example (provenance in the PR that added it). The Claude review is Cortex's (`cdeust/Cortex`): `claude-review.yml` runs at most three reviews per pull request, counted by `scripts/ci_review_budget.py`, each ending with `Verdict: approve` or `Verdict: block`; `pipeline-after-merge.yml` merges a pull request into `main` when its gate succeeded and the review of the same head approves. A merge that waits for its gate or its review ends that run green with a notice, and the run that brings the missing part wakes the resolver again; any other refusal fails it. Both run from the default branch (GitHub runs `workflow_run` from it, and the review action requires its workflow file to match it), so they act once they are on `main`. The review reads `CLAUDE.md` and does not run the tests, which is why the gate runs next to it.

## Secrets broker

Rule: no secret ever enters a worker. The worker is given `ANTHROPIC_BASE_URL` pointing at the broker and a task token as its API key. `modules/broker` (brick 1b.2, `docs/design/platform-v3-srt.md` §2) is that broker: one listener on `127.0.0.1`, port fixed in `modules/broker/broker.json`; the API key in a file giving no permission to its group nor to others (refused otherwise, at start and at each request); task tokens granted and revoked by the gateway with the MCP tools `token_grant` and `token_revoke` on the broker's stdio; only `POST /v1/messages` (and `count_tokens`) to `api.anthropic.com`, the key in `x-api-key`, the body unchanged and admitted by the request policy of 1a.0; one usage record per answer (task, parent, model, tokens, never content) sent to the gateway as `notifications/message`, logger `usage`. Not yet launched by the gateway (brick 1b.4): `compose.yaml` still wires `BROKER_URL`, and workers in compose cannot call Anthropic; tests use a scripted agent. The real call of the broker (T-04R) is `.github/workflows/broker-live.yml`, run on `main` only (push touching the broker, weekly schedule, manual dispatch; never a pull request): `gate.yml` holds no secret, and this workflow holds no credential. It asks GitHub for the identity token of its run and exchanges it at Anthropic for an access token of a few minutes (workload identity federation), which it writes to a 0600 file of the runner, gives to `./aos -- npm run broker:live` as a bearer, and removes. The owner created, once, in the Claude Console: an issuer for GitHub Actions, a service account in a workspace with a low spend limit, and a rule that accepts the token of this repository only. That rule pins the subject of a run on `refs/heads/main` in GitHub's immutable form (`repo:<owner>@<owner id>/<repository>@<repository id>:ref:refs/heads/main`, which this repository emits), the repository and its owner by name and by number, the reference, and the `workflow_ref` claim to `broker-live.yml` on `main`. The last one matters: the two workflows of the Claude Code action also ask for an identity token, and one of them runs in the context of `main`, with the same subject. The four identifiers of the rule (organisation, service account, rule, workspace) are `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID`, `ANTHROPIC_FEDERATION_RULE_ID` and `ANTHROPIC_WORKSPACE_ID`. They give no access by themselves: the rule asks for an identity signed by GitHub for this workflow on `main`. They do name the owner's account at Anthropic, and GitHub prints the environment of a step in the log of a run, which is public for a public repository. They are therefore kept in the secret store of the repository, where GitHub masks a value wherever it would be printed, and not as repository variables (18 November 2026). The owner sets each with `gh secret set <name>`, which reads the value from its standard input, so that no value is on a command line; without one of them the workflow fails at its exchange step and says so. The workflow gives them to one step, through its environment, and to no command line. Two things the wizard of the console does not do by itself, both met on the first run (journal §87): the service account must be a member of the workspace the rule is enabled in, and the workspace identifier given to the exchange must be that workspace's. The job names no GitHub environment, since an environment would change the subject of the token; the environment `broker-live` that GitHub created on 17 November 2026 was deleted the same day, at the owner's word. `features/descriptive/workflows.feature` refuses any copy of the workflow that widens its triggers or permissions, names an environment, stores a secret or traces its commands, any other workflow that exchanges an identity token at Anthropic, and any workflow outside a closed list that asks GitHub for one. Locally, the same run is `ANTHROPIC_TEST_KEY_FILE=<0600 file> npm run broker:live` with a test key of the owner. Other secrets: `GATEWAY_TOKENS` (local development only, token table adapter) and `POSTGRES_PASSWORD` come from the git-ignored local env file or the platform secret store; only `data` and `postgres` receive the database password.

## Postgres, pgvector and migrations

- The database scenarios start a disposable PostgreSQL 17 cluster from the host binaries in `PG_BIN` using `initdb` and `pg_ctl`. They load the `vector` extension. The `gate-linux` judge aggregates the producer reports.
- The three Claude workflows request bubblewrap and socat using the runner’s Ubuntu archive. The five database jobs first use that archive to ensure their host tools and `postgresql-common` are present. The PGDG source references the package-managed key at `/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc`. On both hosted Cucumber shards, APT kept the PGDG build of `postgresql-common` already installed in the image. The shards, lane mutation and replay, and full mutation request PostgreSQL 17 and pgvector from HTTPS `noble-pgdg`, with Ubuntu available for dependencies. The benchmark requests the server alone. [Hosted shard 1](https://github.com/cdeust/architect-os/actions/runs/45846183170/job/140000351898) · [Hosted shard 2](https://github.com/cdeust/architect-os/actions/runs/45846183170/job/140000351801) · [Ubuntu package contents](https://packages.ubuntu.com/noble/all/postgresql-common/filelist) · [PostgreSQL APT repository](https://www.postgresql.org/download/linux/ubuntu/)
- `data/migrations/<NNNN>_<name>.sql`, applied in order, once each, inside a transaction, recorded in `schema_migrations` (`data/src/infrastructure/migrate.ts`). The `data` service applies pending migrations at start.
  - `0001_runs.sql`: registry of executions (`runs`, `run_events`).
  - `0002_memory.sql`: `CREATE EXTENSION vector`, schema `memory`, table `memory.memories` with `embedding vector(384)` and an HNSW cosine index. The dimension must equal `EMBEDDING_DIMENSION` in `packages/contracts/src/data-ops.ts`, which rejects any other length at the API.
  - `0003_runs_immutable.sql`: a trigger refuses any update of a completed run (SQLSTATE 55000, reported as `INVALID_OPERATION`).
- Never edit an applied migration: add a new numbered file.
- Operations: `data/sql/<op>.sql`, listed in `data/sql/operations.json` with their parameters (the SQL of each writes exactly the tables its operation declares in `DATA_OPS.writes`), the SQLSTATEs that mean a named failure (23503 unknown run: `NOT_FOUND`; 55000: `INVALID_OPERATION`) and the shape of the answer. The data image ships `sql/` and `migrations/` (the root Dockerfile copies `data/`).
- Without `DATABASE_URL`, `data` starts with the in-memory store (non-persistent, development only).

## CI

Jobs that run repository commands provision a marked runtime root under the runner temporary directory and invoke those commands through `./aos`. The hosted-runner admission policy requires more than 4 GiB free on the runtime filesystem and more than 2 GiB on the account filesystem. The floors remain provisional. Admission locates the pinned Node version through `tools/runtime/node-locations`, which lists the hosted tool cache for both x64 and arm64.

`.github/workflows/gate.yml` and `.github/workflows/gate-push.yml`: the CI gate (`./aos -- npm run gate`, docs/design/platform-v3-srt.md §7), the first on pull requests, the second on pushes to `main` and on the trial branches of the delivery (`sentinel/gate-1a-*`), with the same jobs (`gate-push.yml` is written whole from `gate.yml` by `./aos -- npm run workflow:gate-push`, never by hand, and `features/descriptive/gate-concurrency.feature` requires the committed file to equal what the command writes; "The two entries of the gate" below) and two required checks, `gate-linux` (two scenario shards with Postgres, a plan job, and one to sixteen mutation/replay lanes planned from the commit: "The planned lanes" below) and `gate-macos` (`features/sandbox/` only), with `contents: read` and `actions: read`. A ruleset on `main` requires both, and a pull request: "How a pull request reaches `main`" below. Typecheck, format and the architecture guard are scenarios of the suite. `claude.yml` is copied from an `anthropics/claude-code-action` example (provenance in the PR that added it). The Claude review comes from Cortex's (`cdeust/Cortex`), hardened here ("The Claude review" below): `claude-review.yml` runs at most three reviews per pull request, counted by `scripts/ci_review_budget.py`, each ending with `Verdict: approve` or `Verdict: block`; `pipeline-after-merge.yml` merges a pull request into `main` when its gate succeeded and the review of the same head approves. A merge that waits for its gate or its review ends that run green with a notice, and the run that brings the missing part wakes the resolver again; any other refusal fails it. `pipeline-after-merge.yml` runs from the default branch (`workflow_run`). `claude-review.yml` runs the file of the pull request's merge commit: its steps before the action run whatever that file says, and only the action refuses to go on when the file differs from the default branch's, so a review is posted once the file is on `main` ("Which commit a run takes its files from" below). The review reads `CLAUDE.md` and does not run the tests, which is why the gate runs next to it.

**The two entries of the gate.** Until 26 November 2026 a run of the gate started 36 jobs whatever it judged (2 Cucumber shards, 16 mutation jobs, 16 replay jobs, 2 verdict jobs); it now starts 7 to 37 ("The planned lanes" below). The account's limit on concurrent jobs is shared by all its runs. Measured on the runs of `gate.yml` from 21 to 26 November 2026 (UTC), when it was the only entry, declared no group and started 36 jobs: in the sample first taken, the latest 100 rows of the API minus 8 cancellations, 92 runs, a run with no other gate run in flight took 8.6 minutes (median) and a run with ten overlapping runs 54.0 minutes; the full window, paginated, holds 145 completed non-cancelled runs and 59 pairs of overlapping runs on the same pull-request branch, where the older run held runners for a verdict no one reads.

The runs of one pull request therefore share a concurrency group, and a new commit cancels the run of the commit it supersedes. The runs of a push must not be cancellable that way: a run on `main` publishes the base of the count that the next run reads, and a run on a trial branch is the one the delivery waits for. One workflow file cannot say both. `cancel-in-progress: false` says what the run that declares it does to the others; it does not protect that run from a later run, of any workflow, that names its group. A group cannot be empty, and `concurrency` has no conditional form (GitHub, "Control the concurrency of workflows and jobs"). So the gate has two entry files:

| Entry                             | Name        | Trigger                                                           | `concurrency`                                                                                                    |
| --------------------------------- | ----------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `.github/workflows/gate.yml`      | `gate`      | `pull_request` alone, so that every run has a pull-request number | `group: gate-pr-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`, literal, at workflow level |
| `.github/workflows/gate-push.yml` | `gate-push` | `push` to `main` and to `sentinel/gate-1a-*`                      | no key, at workflow level nor on a job                                                                           |

`gate-lane.yml`, which both call, declares no key either: GitHub warns that a group of the same value in a called workflow cancels its caller. From the line `jobs:` to their end the two entries are the same bytes. The duplication is deliberate: the rulesets require the contexts `gate-linux` and `gate-macos`, a required check takes no account of the workflow nor of the event, and a job of a called workflow reports as `<job name> / <reusable job name>` (GitHub, "Troubleshooting rules"), so both verdict jobs must be jobs of each entry. Checked on 26 November 2026: the ruleset of `main` requires exactly those two contexts, and the jobs of run 45771449037 are named `gate-linux`, `gate-macos`, `gate-linux-cucumber-1`, `gate-linux-lane-1 / mutation` and so on. `features/descriptive/gate-concurrency.feature` holds the rule: the literal block of `gate.yml` and its one trigger, no key in `gate-push.yml` nor in `gate-lane.yml`, no group whose name begins with `gate-` in any other file of `.github/workflows` (`.yml` and `.yaml`, workflow level and jobs, both forms of the key), equal bytes for the jobs, and each reader below naming its entry. It compares literal values and evaluates no expression.

What cancellation does, as observed. It has no single job outcome: in the 22 cancelled runs of 21 to 26 November 2026, `gate-linux` failed at `Require all producers` every time, and `gate-macos` succeeded in 20 and was cancelled in 2. A cancelled run can leave artifacts: the cancelled `main` run 45162457452 retained `gate-base-macos`, which the `status=success` filter of the lookup makes ineligible. A rapid second push, or the rerun of an older run, can cancel the run of the current head of a pull request, since the group admits runs in the order they are queued and not in the order of the commits. That fails closed: the head has no green check until its run is started again, and a green is never carried to another SHA.

Limits, written. The group frees no runner between two different pull requests, which still share the limit. A workflow of a pull request can name the group `gate-pr-<n>` of another pull request, and the scenarios cannot see a group that a workflow computes at run time; either can only cancel a pull-request run, since no other run of the gate is in a group.

The run the delivery reads is bound to its workflow, the push event, its trial branch and the SHA together (`GhForge.run`, `tools/deliver/src/infrastructure/gh-forge.ts`). Before 26 November 2026 it took the lowest run id that matched the display name of the workflow and the head SHA, whatever the event or the branch: a successful pull-request run for a head H, which judged a synthetic merge commit and not H, could come first, and `deliver --until ci` could report `ready` while the trial push for H was pending or had failed; a run of `gate-push` for the same SHA on `main` or on another trial branch could also match. A run of another event, of another branch or of no branch is now not the run of the push (`tools/deliver/features/ports.feature`, « a run started by a pull request, and a run of the push to another branch, are not the run of the push »; journal §124).

When run 45857093429 started for the next commit, both the older attempt and the replay ended as cancelled. A push to `main` after integration must restore the base from its pre-split parent, publish both new base artifacts, and leave them available to the following run. Before downloading evidence, the judge checks the jobs of every numbered attempt and the artifacts of the run. Each response must contain at least one page. For each collection, every page’s `total_count` must equal the combined row count, and every row must have a distinct positive integer ID. This also checks jobs and artifacts outside the judge’s plan. [Attempt jobs REST response](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt) · [Run artifacts REST response](https://docs.github.com/en/rest/actions/artifacts#list-workflow-run-artifacts)

A run has five fixed jobs (two Cucumber shards, `gate-linux-plan`, `gate-linux`, `gate-macos`) and two per planned lane: 7 for an empty perimeter, 37 at most. On PR #152 the plan job took 20 seconds, from 13:44:22 to 13:44:42 UTC. GitHub started the two announced mutation jobs and both independent replay jobs.

The re-derivation guarantees one thing: for a given code of the gate, neither a lane nor the output of the plan job removes a mutant from the judgement. A pull request controls its own tree, the workflows and `tools/test-gate` included; a rewrite of the gate is for the review to refuse (R-6).

The delivery names the three fixed producers of `gate-linux` and a family, `plannedProducers` in `tools/deliver/deliver.json` (`gate-linux-lane-<n>` followed by ` / mutation` or ` / replay`). Each planned prefix reserves every job name beginning with it. The reserved sets of two families must be disjoint and no required job or named producer may lie inside a reserved set. Two prefixes may share leading characters when neither is a prefix of the other. Fixed producers can be shared by explicit dependencies, and a required leaf may also be an upstream job. Within a family the complete names must be unique for the lane numbers the run actually shows. A custom job outside all these names has no bearing on the verdict. The configuration reader retains every own JSON job label, including labels that also name JavaScript properties. If any aggregate has a planned family, Deliver reads every numbered attempt, even when it already found all fixed producers. Every page must give the full count of jobs in that attempt. The combined rows must match the count and each execution must have a distinct positive integer ID. An incomplete response stops delivery because it could hide an inherited failed lane. Given complete pages, Deliver takes the newest execution of each name. It requires the complete names of the lanes 1 to n without a gap, and does not derive the plan: the first parent of the local gate is not always that of the hosted run. A job of the family whose name holds no lane number is a failure, never a missing runner.

Still to measure: the job name when the plan fails before producing a matrix, and the wall time of an isolated run compared with one under contention.

### How a pull request reaches `main`

On 26 November 2026 the owner decided three things (journal §112). `main` takes pull requests only, and no actor bypasses its ruleset. A pull request merges when the gate is green and both reviewers, Claude and Codex, approved the exact commit. The expected ruleset is a committed file, and a scenario is red when that file is weakened.

**The delivery opens the pull request.** `./aos -- npm run deliver -- <name>` (`tools/deliver`, journal §124) never pushes `main`. Its phases: the preconditions (a clean tree; the commit descends from `main` and from the work branch `deliver/<name>` when there is one; the append-only files only grew; `steps/<name>/record.json` is in the commit and its schema accepts it), a push of the trial branch, the gate, the CI of that push for the same commit, then the publication: both branches are read again, the work branch is pushed without force, and a pull request is opened from it to `main` (`destination` in `tools/deliver/deliver.json`), never as a draft (`-F draft=false`), or the one already open for that head and base is found and given back. Nothing in the delivery merges it. Its title is the template `pullRequestTitle` of the file with the name; its body is rendered by the host from the record of the commit alone (the verdict and findings of each review and the status of each acceptance criterion, the checks, the SHA-256 of the inputs and of the launcher files, the tree the step saw), every value in a code span with `@`, `#`, `:` and the closing keywords broken by a zero-width space, so that the body mentions no account and links or closes no issue. The forge opens nothing when it does not see the work branch at the delivered commit. A name or a file that would make the delivery push `main` is refused before any act (`la destination n'accepte qu'une pull request`). What a rerun does: the work branch already at the commit is not pushed again, and the open pull request is found, not doubled. Proven against scripted ports and a scripted client of the forge; the call against GitHub has not been played.

**The ruleset.** `docs/design/ruleset-main.json` is the body that recreates the ruleset of `main` (id 27467434): `gh api -X PUT repos/<owner>/<repo>/rulesets/<id> --input docs/design/ruleset-main.json`, or `-X POST repos/<owner>/<repo>/rulesets` where there is none. It holds five things: the branch is not deleted (`deletion`), it is not rewritten (`non_fast_forward`), a commit reaches it through a pull request (`pull_request`, with no required approval, no code-owner review, no approval of the last push and no thread to resolve), two checks named `gate-linux` and `gate-macos` are required (`required_status_checks`), and `bypass_actors` is empty, so the owner's role is refused like any other. The file was written from the live ruleset on 26 November 2026, after the owner changed it that day, and was equal to it on its six keys:

```bash
gh api repos/<owner>/<repo>/rulesets/27467434 | jq -S '{name,target,enforcement,conditions,bypass_actors,rules}' > live.json
jq -S . docs/design/ruleset-main.json | diff - live.json
```

What the two required checks are worth is narrower than "both jobs of the gate succeeded". The ruleset names two contexts, not the workflow that reports them. GitHub counts `success`, `skipped` and `neutral` as satisfied ("Successful check statuses are success, skipped, and neutral"; a job skipped by a conditional "reports Success": docs.github.com, "Troubleshooting required status checks"). And GitHub runs `gate.yml` for a pull request as the merge commit of that pull request has it (`pull_request`: "GITHUB_SHA … is the last merge commit of the pull request merge branch", "Events that trigger workflows"). A pull request of this repository can therefore rewrite `gate.yml` so that two jobs with those names succeed, or are skipped, without running the gate, and the ruleset is satisfied. A check can be bound to one app as its expected source ("Available rules for rulesets"), which does not help here: the workflow of `main` and the workflow of the pull request are both jobs of GitHub Actions.

`features/descriptive/ruleset-main.feature` loads the file through its one reader (`features/steps/ruleset-main.ts`) and refuses thirty broken copies, each by the words of its refusal. The reader holds the decided policy value by value: the text must be the canonical form of what it parses to, so a key written twice is refused (`JSON.parse` would keep the last); the shape is strict; what a weakened copy lets through is named; and every value must be the one decided, so a key the live ruleset does not carry, and a policy that is stricter or other (one required approval, a branch up to date, another order), are refused too: such a change is a decision, made in the reader and the file in one pull request. Refused by name: a bypass actor (the administrator role, an app limited to pull requests); no `pull_request` rule; no `required_status_checks` rule, a second one that names no check, one without `gate-linux` or without `gate-macos`, a third check, a check bound to one app, checks not required when the ref is created; an enforcement that is `disabled` or `evaluate`; `refs/heads/main` not included, a pattern beside it, any excluded ref; no `deletion`, `deletion` twice, no `non_fast_forward`; merge methods without `squash`, which the resolver asks for; an unknown key, an unknown rule, no bypass list.

The scenario reads the file, not the setting of the repository. Nothing automated compares the two: the comparison is the two commands above, run by someone who holds the administrator's credential. `tools/watch` does not do it, for a reason observed on 26 November 2026. A read of the ruleset without a credential answers 200 with `id`, `name`, `target`, `source_type`, `source`, `enforcement`, `conditions`, `rules`, `node_id`, `created_at`, `updated_at` and `_links`, and with neither `bypass_actors` nor `current_user_can_bypass`; the same read with the owner's token has both. GitHub's reference says so ("Get a repository ruleset": "To prevent leaking sensitive information, the `bypass_actors` property is only returned if the user making the API request has write access to the ruleset"), and writing a ruleset takes the repository permission "Administration" in write. The token of a job of `watch.yml` (`contents: read`) therefore cannot say that no actor bypasses, and a job given a token that can would hold the right to edit the ruleset. What a read without a credential does give is `updated_at`, equal that day to the one the owner's token reads: a job could flag that the ruleset was edited since a recorded date, and leave the comparison to someone with the administrator's credential. That monitor is not built; whether every edit, a bypass actor included, moves `updated_at` was not tried, since it takes an edit.

### Bubblewrap before the scrub

The shape: the action is used in the steps of a job and nowhere else in the document (a group of parallel steps included); the workflow, the job and each of its steps have no key outside a closed list; the job runs on `ubuntu-24.04` and holds one action, the pinned one, scrubbed, with the inputs written for its file, chosen by the name of the file and compared whole, the prompt by its presence and not by its text (the action keeps the last permission mode it is given, in either spelling: `lastPermissionMode`, `base-action/src/parse-sdk-options.ts` at `4411a9e9`); its condition is the exact text written for its file, with the credential of the security review in that file alone; the step just before it is the proof, to the letter; the step `settings` is the installer written for its file, to the letter, fed by a sparse checkout of the commit of the run. It does not compare the text of the prompt, nor the other steps of the job. A property of the same feature tries every change of one key of the checkout of the settings, their installer, the proof and the action of each committed file (deleted, replaced, a character more, an unknown key added), and all are refused but a prompt given another text. Whoever can change a workflow can change that rule in the same pull request: the boundary is the review, and a credential that cannot write workflows, which is the open defect below.

Not known: what Claude Code does when bubblewrap is installed and cannot create a namespace. The initial Ubuntu 24.04 VM trial exercised the namespace probe alone. The subsequent GitHub security review completed under the scrub. The general PR review and the `@claude` workflow still need hosted runs that reach the model with the integrated configuration. ### Which commit a run takes its files from

GitHub chooses the commit of a run by its event (docs.github.com, "Events that trigger workflows", the columns `GITHUB_SHA` and `GITHUB_REF` of each event): the last commit of the default branch for `issue_comment`, `issues` and `workflow_run`; the merge commit of the pull request for `pull_request`, `pull_request_review` and `pull_request_review_comment`. The workflow file is read at that commit, `github.sha` is that commit, and a checkout without `ref` takes it.

| Workflow                     | Event                                                | Workflow file, job condition, steps, managed settings | Tree Claude works in                                                                                                                                 |
| ---------------------------- | ---------------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `claude.yml`                 | `issue_comment`, `issues`                            | Default branch                                        | On an open pull request, its head, which the action checks out before Claude starts (`setupBranch`, `src/github/operations/branch.ts` at `4411a9e9`) |
| `claude.yml`                 | `pull_request_review`, `pull_request_review_comment` | Merge commit of the pull request                      | The head of the pull request, checked out by the action in the same way                                                                              |
| `claude-review.yml`          | `pull_request`                                       | Merge commit of the pull request                      | The head of the pull request, checked out by the action over the checkout of `main`                                                                  |
| `claude-security-review.yml` | `pull_request`                                       | Merge commit of the pull request                      | `main` (`ref: main`); the pull request reaches Claude as a diff                                                                                      |

The script of the proof reads nothing of a pull request. But on every row that says "merge commit", the step is whatever the pull request makes of the workflow file: a pull request of this repository that changes the file changes the script that runs under `sudo`, the condition of the job and every other step. The scenarios judge the committed files.

**Open defect of `main`, older than this step and not closed by it.** On those rows the job is given `secrets.CLAUDE_CODE_OAUTH_TOKEN`, so an account with write access to this repository can open a pull request whose workflow file hands the subscription token to a step it wrote. In `claude-review.yml` and `claude.yml` the action checks that the workflow file equals the default branch's, but inside the action, after the steps before it. In the security review nothing checks it: the job passes its own `github_token`, and the action returns that token before the exchange that validates the workflow (`setupGitHubToken`, `src/github/token.ts` at `4411a9e9`). The correction is the local branch `claude-secrets-environment`, not merged: the subscription token given only to files of `main`, through an environment, with `pull_request_target` for the review and `workflow_run` for the security review.

### The Claude security review

`.github/workflows/claude-security-review.yml` reviews a pull request for security, once, when it is opened, reopened or marked ready; the pushes that follow are not reviewed. It runs on the owner's subscription (`CLAUDE_CODE_OAUTH_TOKEN`, the secret of the two other Claude workflows), and blocks nothing: neither the resolver of `pipeline-after-merge.yml` nor the ruleset of `main` names it. The reviewer publishes nothing: it has no tool to post, and returns its findings as JSON of the shape of `.github/claude-security-review/findings.schema.json` (`--json-schema`). A second job, `publish`, with no model and no secret but its own token, checks that JSON with `.github/claude-security-review/publish.py`, neutralises what a reader could act on (each field is one code span on one line, where GitHub renders no link, image, HTML nor entity, and a line that holds it begins with a backtick or a prefix, never with `Verdict:`; `@`, which an app such as Codex obeys whoever writes it, becomes `＠`), refuses an answer that holds the shape of a credential (`sk-ant-`, `gh[opsur]_`, `github_pat_`), read after removing the format characters that render as nothing (category Cf: zero-width, joiners, soft hyphen, direction marks) and folding compatibility forms, and posts one comment as `github-actions[bot]`, whose comments the resolver never reads (it reads `claude[bot]` only). A refused answer posts a fixed notice, and the job summary names where in the schema it failed, never a byte of what it held (the summary is rendered too); `NaN` and `Infinity` are refused. It stays advisory until its false positives have been counted on this repository. The audit and its filter are `.github/claude-security-review/scan-instructions.txt` and `false-positive-filtering.txt`, adapted from `anthropics/claude-code-security-review` at `0c6a49f` (MIT, notice and provenance at the head of each file); the restriction of Claude Code is `.github/claude-security-review/managed-settings.json`. `features/descriptive/security-review.feature` holds the rules below, each with a broken copy the rules refuse.

The engine is `anthropics/claude-code-action`, at the pin of `claude-review.yml` (v1.0.290, Claude Code 2.1.332 from its lockfile), in agent mode: a prompt, no `track_progress`, `--permission-mode default`. Agent mode keeps the checkout of `main` and fetches nothing of the pull request (`src/modes/agent/index.ts` at `4411a9e9`); tag mode, which `track_progress` selects, checks out the head of the pull request. The guards hold whatever engine runs in the step `engine`.

The audit is a versioned prompt, not the command `/security-review` of Claude Code: the documentation and examples of `claude-code-action` (v1.0.290) give no command for a security review, only a prompt (its `solutions.md`, "Security-Focused PR Reviews"), and the built-in `/security-review` of Claude Code 2.1.332 runs `git diff origin/HEAD...` with Bash on a checkout of the head of the pull request: a three-dot diff is a merge-base comparison, which this repository refuses in CI, and Bash and the PR head on disk are what the guards below refuse. Its text is the audit prompt of `anthropics/claude-code-security-review`, which the scan instructions adapt.

The action of Anthropic, `anthropics/claude-code-security-review`, is not the engine. Read at `0c6a49f1fa56a1d472575da86a94dbc1edb78eda`, the head of its `main` on 25 November 2026 (no release):

- it requires an API key, billed per use: its scan step sets `ANTHROPIC_API_KEY` from `claude-api-key` and exits 1 when it is empty, `validate_claude_available()` refuses to run without it, and its filter builds `Anthropic(api_key=…)`, sent as `x-api-key`, which a subscription token is not; in non-interactive mode Claude Code takes `ANTHROPIC_API_KEY` before `CLAUDE_CODE_OAUTH_TOKEN` and sends it as `X-Api-Key` (code.claude.com/docs/en/authentication, "Authentication precedence");
- its default model, `claude-opus-4-1-20250805`, was retired on 5 August 2026;
- its false-positive filter is inert: `validate_api_access()` calls `claude-3-5-haiku-20241022`, retired on 19 February 2026, and on that failure the filter turns itself off with a warning, so `false-positive-filtering-instructions` is never read and only its hard-coded exclusions apply;
- its dependencies are not fixed by its SHA: `npm install -g @anthropic-ai/claude-code` takes `latest`, `pip install` takes `PyGithub>=1.59.0`, `requests>=2.28.0`, `anthropic>=0.39.0`, and it sets up Node 18 and Python `3.x`;
- it saves its once-per-PR cache marker before it checks its key, so a run without the key spends the only review of the pull request;
- its README says it is not hardened against prompt injection and should review trusted pull requests only.

It could become the engine when it takes a subscription token, its default and validation models are current, and its installs are pinned; `tools/watch/watch.json` watches its `action.yml` and its prompt (`claudecode/prompts.py`) to say when they move.

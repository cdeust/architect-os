# Testing

Every test is a Gherkin scenario run by `@cucumber/cucumber` (`./aos -- npm test` is `cucumber-js`, after `tsc -b`: the platform launches its modules and workers from their built entry points). Typecheck, format and the architecture guard are scenarios too, so `./aos -- npm run check` is `./aos -- npm test`. No scenario of the default profile calls Anthropic or a host beyond the loopback: scripted models stand in for the API, and the escape scenarios, which try `example.com` and `169.254.169.254` from inside a sandbox, must fail to reach them; the one scenario that calls the real API is the live profile (`./aos -- npm run broker:live`). The CI gate (`./aos -- npm run gate`, `docs/design/platform-v3-srt.md` §7) adds the pickle count and mutation testing on top.

## Rules of the suite

- One `cucumber.mjs`: `paths` over both layouts, `retry: 0`, `strict: true`, no `tags`, no `name`. A skipped, pending or undefined step is a failure.
- No computed `Examples` table: every row is literal in the `.feature`.
- Step text is unique across the repository (all steps load in one run; an ambiguous step fails).
- Steps are strict TypeScript using `node:assert/strict`, typechecked by `./aos -- npm run typecheck`.
- No scenario is conditional on the host. A scenario that needs Postgres or srt and cannot get it fails.
- « Committed », in a title or a step, is the file as it stands in the tree the suite runs on: in the gate that is the commit, on a workstation it is the working tree, and a scenario that needs the difference says so.

## Running

Configure a marked runtime root as in the [quick start](../README.md#quick-start). From the repository root:

```bash
./aos -- npm test                         # full default suite, including typecheck
./aos -- npm run gate                     # scenarios, changed-line mutation and independent replay
./aos -- npm run gate -- --job macos      # sandbox scenarios
```

Stryker's first run (the whole `mutation` profile, before any mutant) has an explicit bound of 20 minutes (`dryRunTimeoutMinutes`), a fuse against a run that never ends: the default of 5 minutes was reached silently on 18 November 2026, when that run took up to 4 min 49 s and the suite kept growing.

One set of scenarios is outside the gate, with its own profile in `cucumber.mjs`: `modules/broker/live/` spends on the real API with a real key, and is a command of the owner. It is not counted by the gate, and mutation does not apply to it: it adds no production line of its own.

Positional paths given to `cucumber-js` are merged with the `paths` of `cucumber.mjs`; they add to the run instead of narrowing it. To run one feature after typecheck, use the empty-path replay profile, for example `./aos -- npx cucumber-js --profile replay features/sandbox/session-locations.feature`. The `macos` profile of `cucumber.mjs` runs `features/sandbox` alone.

## Gate mutation perimeter

Git lists changed paths in the raw diff and counts lines using LF. The gate refuses changed production sources containing a lone CR, U+2028 or U+2029 with `GATE_SOURCE_LINE_SEPARATOR`. CRLF is one line break for both Git and Stryker. `GATE_MUTATION_PATH_PATTERN` refuses paths containing glob metacharacters, backslashes or line terminators before the gate builds a mutation pattern.

The gate reads only regular files. It opens source paths without following a link in any component, and refuses a current symlink in the raw diff before asking for its patch. `GATE_SOURCE_LINK` names the refused path. Source paths stay within the checkout, and reports use their admitted directory. The directories that can hold production sources (a directory segment of a production glob, compared after Unicode normalization and case folding) are walked on disk without following a link, whatever git lists, ignores or keeps unchanged from the first parent; a link found there, where a source or a directory of sources could be, is refused with `GATE_SOURCE_LINK`: the sources Node loads through it would be in no perimeter.

Stryker derives the report file list from mutant results. For a requested file whose result is missing or empty, the gate directly instruments its checkout source. It accepts an empty result only when no discovered mutant overlaps any changed line. It still checks that source for mutation directives. The regression scenarios are in `tools/test-gate/features/mutation-perimeter.feature` and `tools/test-gate/features/mutation.feature`.

## `@postgres`: a disposable database

Scenarios tagged `@postgres` (the `postgres` rows of the data-store contract) get a real database from the hook in `features/support/postgres.ts`: the first one starts a disposable Postgres 17 with pgvector, from `PG_BIN` or the `pg_ctl` found on `PATH`, listening on a Unix socket only (no TCP), and each scenario gets a fresh database. Without a PostgreSQL the scenario fails; it is never skipped. A detached watchdog (`features/support/pg-watchdog.mjs`) stops the server and removes its directory when the test process is gone, however it died (Stryker kills its workers, so `AfterAll` may never run, and an orphan server keeps a SysV shared memory segment; macOS allows 32); `features/infra/postgres-watchdog.feature` proves it with a SIGKILL.

## End to end

Nothing here is composed for a test where the production code can compose it:

- `features/sandbox/gateway-entry.feature`: the process is `node gateway/dist/src/serve.js`, given only its configuration. It starts `data` and the broker as its children, the module and the worker under a real srt, and serves a real MCP client over HTTP, before a fake model over HTTPS.
- `features/sandbox/gateway-native.feature`, `features/sandbox/recall.feature`, `features/sandbox/remember.feature`: the platform composed by the production code, under a real srt.
- `features/integration/gateway.feature`, `features/integration/agent-worker.feature`, `features/integration/usage.feature`: the same paths in one process over streams, the sandboxes replaced by in-memory runners; the worker runs the real Claude Code binary against a fake model on the loopback.

No scenario calls the real API: `modules/broker/live/` is the owner's command for that, outside the gate.

## Port contracts

A contract is one `Scenario Outline` per case with one `Examples` row per adapter. Adding an adapter means adding one row to each outline. Example: `data/features/data-store-contract.feature` runs the same six cases on `in-memory` and on `postgres`. The `Examples` of `features/descriptive/claude-files.feature` list the committed `.claude/agents` and `.claude/commands` files: a new file adds its row.

### The fingerprint of the tree, the record of a step and the folder `steps/`

- The fingerprint (`packages/sandbox/features/tree-fingerprint.feature`), on a throwaway repository with one commit: a clean tree is the tree of its commit; a changed tracked file and an added untracked file each give the tree that committing everything would give (the scenario commits and compares); an ignored file leaves the tree clean; the same content gives the same tree twice and another content another tree; the index of the worktree is not touched (`git status --porcelain` and the bytes of `.git/index` are the same before and after) and the temporary directory (made under a `TMPDIR` the scenario owns) is left empty, on a failure too. A fake `git` first in `PATH` records the six fingerprint calls: the exact argv with `--attr-source=<the empty tree> -c core.fsmonitor=false -c core.hooksPath=/dev/null -c diff.ignoreSubmodules=all`, the directory they run in, the temporary index for `read-tree`, `ls-files -s -z`, `add` and `write-tree` only. With real git (rule « what a session wrote in the tree decides nothing of what git does for the fingerprint »): an `ident` attribute of the tree does not change the bytes that enter the fingerprint (the blob of the tree is the raw hash of the file on disk); a repository nested in the tree, with a witness program as the `clean` filter of its own configuration, is refused with a fixed message, not tracked or recorded by the commit, and the witness does not run; the same witness runs under a `git status` started without the options, so that those scenarios can fail. A call that exits 3, or prints what is not 40 lower-case hexadecimal characters (a marker, 39, 41, upper case), throws the fixed message that names the call and carries nothing git printed; a bound of one millisecond is exceeded by the real git; a directory that is not a repository throws the same message.
- The record and the publication (`packages/sandbox/features/step-record.feature`, with in-memory dependencies for the fingerprint, the clock, the launcher and the folder `steps/`): the exact record of a step with a scout, a check and a review, the files published byte for byte, hashes equal to those of the published files and of the launcher files as read, the JSON on two-space indentation with a final line break; the three kinds of refused step publish with `outcome` `refused` and only what ran; a brief rewritten during the build is published as it was read; a name already taken, a folder name the expression refuses (and its edges, 1 and 32 characters), a fingerprint that throws and a launcher file that cannot be read are exit 2 before any session and publish nothing; a publication that fails prints no summary line; a model name from a stream that the expression refuses is counted under `other`; a finding, a report and the output of a check carry a marker that is found in no published file. With the real folder on a temporary worktree (umask 0, so that the mode 0644 is the one the code asks for): `steps` absent is created; `steps` a link or a file is refused, by `exists` and by `publish`, and nothing is written behind the link; `steps/<name>` already there as a file, a directory, a dangling link or a link to a directory outside exists, is refused and is left as it was; a folder that appears between the check and the writing is refused again. The real dependencies of a process give the launcher files as committed, the clock, the fingerprint of `INIT_CWD` and its folder `steps/`.
- The folder (`features/descriptive/steps.feature`): the rule of one folder is a function (`features/steps/steps-folder.ts`) that the committed folder `steps/` and seventeen broken copies of a valid folder go through. The committed folder is absent or empty until the launcher that runs this code publishes the first one: the scenario then passes on nothing, and its name says so.
- The builder profile denies writing `${worktree}/steps` and editing `steps/**` (`packages/sandbox/features/profile.feature`). The proof in a real sandbox is `features/sandbox/escape.feature`: three attacks of the builder on `steps/` of its worktree (rewriting the record of a step already published, forging a folder beside it, replacing the empty folder the host prepared by a link), each with its witness on the host without srt, and a positive control that the builder still writes elsewhere in its worktree.
- Inputs invented by a fresh session (`packages/sandbox/features/step-record-fresh.feature`, 103 scenarios written with the existing steps, each expectation taken from the design and not from the code; journal §99): unusual names and bytes in the inputs, the launcher files one by one, the record at its limits, what `steps/` may already hold, unusual file names and exclusion rules for the fingerprint. Four failed on the host when they were written and found three defects, fixed since.
- The root of the worktree is the one `resolveWorktree` gives (`packages/sandbox/features/step-record.feature`, with the real dependencies on a real linked worktree): launched from a directory below the root, the step is refused and nothing is created; outside a linked worktree, the refusal is the one of `resolveWorktree`. An input is read as UTF-8 text with its byte order mark kept, and three sequences that are not valid UTF-8 are refused. In `packages/sandbox/features/measure.feature`, a model named `__proto__` keeps its cost, and a `modelUsage` that is null, a list or a number is not a result. In `features/descriptive/steps.feature`, the rule judges what git could commit under the folder: a file or a directory the repository ignores, and an empty directory, are not judged; a file that is not ignored is still refused, the exclusion file of the host is not read, a folder that is tracked is judged like one that is not yet, and a path git still lists that the disk no longer holds gives a reason instead of an exception.

### The closed environment of git (docs/design/orchestration-fable-5-2.md §14, « Un environnement fermé pour git »)

Git, and the client of the forge, receive a closed list of variables taken from the host by name, then what the caller sets itself; nothing else. What proves it, at each place:

- The fingerprint of the tree (`packages/sandbox/features/tree-fingerprint.feature`, `tree-fingerprint-fresh.feature`). Its git receives five names of the host (`PATH`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`), `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to an empty file, `GIT_ATTR_NOSYSTEM=1` to disable system attributes, and `GIT_INDEX_FILE` for the calls on the temporary index: it reads no configuration of the machine, and `HOME` is not given. With real git and throwaway repositories: a `GIT_DIR` and a `GIT_WORK_TREE` of the process that name a second repository leave the fingerprint of the first; a `GIT_CONFIG_COUNT` that makes `core.autocrlf` `input`, with a file that has CRLF line ends, leaves the tree the one that committing everything would give; so does a host whose configuration converts line endings and excludes `local.txt`, written in the `.gitconfig` of the `HOME` of the process, in the `git/config` of its `XDG_CONFIG_HOME`, and in the two default exclusion files git reads even without a configuration (`$HOME/.config/git/ignore`, `$XDG_CONFIG_HOME/git/ignore`): putting `HOME` back in the list alone makes that scenario fail. With the fake `git` (a script of node that reads its answers from files beside itself and writes the names of its environment): each call holds exactly the names of the five that the process had set, the two configuration variables, and `GIT_INDEX_FILE` for `read-tree`, `ls-files -s -z`, `add` and `write-tree` only; a `HOME`, a `GIT_DIR`, a `GIT_CONFIG_COUNT` or a `GH_TOKEN` of the process is never received.
- The gate (`tools/test-gate/features/closed-environment.feature`, `closed-environment-fresh.feature`), on the disposable repositories of the gate. Its git receives the same five names and the same three fixed Git settings. The lease also disables system attributes. The second repository has two commits and the `GIT_DIR` of the process names it; what is expected (head, first parent, diff) is recorded through the production git (`GitRepository`) before the poison is set, and what the gate then reads is that of its own repository. In the fresh file, a `HOME` whose `.gitconfig` sets `core.autocrlf` and an `XDG_CONFIG_HOME` whose `git/config` sets `diff.noprefix` change nothing: the diff of a file with CRLF line ends is read back with them, and with its prefixes. The literal check of the three production files that start git (none gives `process.env` to a launch, and a copy that does is refused) is in `features/arch/closed-git-environment-text.feature`: it is in `features/arch`, which the mutation profile leaves out (the reason is written in `cucumber.mjs`).
- The delivery (`tools/deliver/features/command.feature`, rule « the environment of the process is not given to git nor to the client of the forge », and `host-process.feature`), on the real adapters, the throwaway repository and its bare remote: with a `GIT_DIR` that names another repository the delivery pushes the commit of its worktree to its own remote; with `GIT_CONFIG_COUNT=1` injecting `url.<other remote>.insteadOf=<its remote>` the push reaches its own remote and the other holds no branch; with `GIT_SSH_COMMAND` and `GIT_ASKPASS` naming a witness program and a remote that only ssh could reach, the witness file is not written, and the same witness is written when git is started with those variables (so that the first scenario can fail); the scripted client of the forge writes the names of its environment, and each call holds exactly the names of the list of `deliver.json` that the process set, `GH_TOKEN` among them. The `XDG_CONFIG_HOME` that git and the client of the forge receive is the one of the variable `ARCHITECT_OS_HOST_XDG_CONFIG_HOME`, which the entry `./aos` sets to `set:<value>` or `unset` from what its caller had, before it gives the command the `XDG_CONFIG_HOME` of the run (which the nested gate keeps): absent, as in a delivery started without `./aos`, the delivery takes the `XDG_CONFIG_HOME` of its process as it is; `unset` gives none, `set:` an empty one; empty or of any other form, the delivery refuses, exit 2, before it starts any program (`tools/deliver/src/main.ts`, `hostEnvironment`; `tools/deliver/features/environment-fresh.feature`, and through the launcher `features/arch/runtime-entry.feature`). A `./aos` started inside an admitted run sets that variable again, from the `XDG_CONFIG_HOME` of the outer run, as decided: a delivery started through it gives git and the client of the forge the configuration of that run, not the one of the first caller. `closedEnvironment` has its own table (the names the host sets, then the added ones, which win; a name the host leaves undefined is absent), `runToEnd` is given a complete environment and nothing of this process is added, and `runToFile`, which starts the gate command, is shown to inherit it. The `environment` key has its schema scenarios in `tools/deliver/features/config.feature`: the closed set of ten names (one name, four, all ten), and the refusals at the position of the name: no name, a name twice, a value that is not a list or a name, an empty name, lower case, a leading digit or `_`, a `-`, a space, an `=`, a line break, and a name outside the set (`A`, `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `GIT`, `constructor`, `GIT_DIR`, `GIT_`, `GIT_CONFIG_COUNT`).
- The suite (`features/descriptive/closed-git-environment.feature`): `features/support/git-environment.ts` removes the `GIT_` variables of `process.env` when the suite loads. A child `node` started with `GIT_DIR=/nowhere`, `GIT_EDITOR=x` and `GITHUB_TOKEN=y` prints the names of its variables that start with `GIT`: all three when it does not import the file (the child is the proof that the variables were there), and only `GITHUB_TOKEN` when it does. The child receives these three, `PATH` and, when the suite has one, `TMPDIR`, and nothing else: the names it prints do not depend on the environment of the host. The helpers that set a `GIT_` variable for a scenario set it after the file ran and restore it at the end.
- The rule is kept by a literal check, `features/arch/closed-git-environment-text.feature`, which lives under `features/arch`, which the `mutation` profile leaves out (`cucumber.mjs`): it reads `packages/sandbox/src/tree-fingerprint.ts`, `tools/test-gate/src/infrastructure/git.ts` and `tools/deliver/src/infrastructure/host-process.ts` as text and fails when one of them spreads `process.env`, writes `env: process.env`, or passes `process.env` as an argument; one broken copy per file, with `process.env` spread back into its launch, is refused, and `process.env[name]` and `process.env.HOME` are not. The throwaway repositories of the scenarios are built by git started with a closed environment too: `PATH`, and the two configuration variables at `/dev/null` (the fixtures of the fingerprint, of the gate and of the delivery, and `features/steps/steps-folder.ts`).
- The names the gate's git receives (`tools/test-gate/features/closed-environment.feature`, rule « the git of the gate receives exactly the names of its list that the process set »): a fake `git`, an executable script the step writes in a temporary directory and puts first on the `PATH` of the process, records the names of its environment and its arguments. With the five names set (and a `HOME`), it received exactly those five and the two configuration variables, both `/dev/null`, and no `HOME`; with one of `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR` unset, the other four and the two variables; with `GITHUB_TOKEN`, `NODE_OPTIONS` or `GIT_EXEC_PATH` set, still the same. Broken by hand: a name of the list emptied, the list emptied, or the loop emptied fails these scenarios. The condition `if (value !== undefined)` was removed from `closedEnvironment`: with `if (true)` all ten scenarios passed, because node leaves a variable given as `undefined` out of the environment of the child, so the mutant was equivalent; the scenarios on an unset name prove that this is what happens.
- The options of the three launches: the fake git of the gate is started as `--attr-source=4b825dc642cb6eb9a060e54bf8d69288fbee4904 -c core.quotePath=false -c core.fsmonitor=false -c core.hooksPath=/dev/null -c diff.ignoreSubmodules=all rev-list --parents -n 1 HEAD`; the fake git of the delivery in `tools/deliver/features/ports.feature` is asked each of its seven tested commands after `--attr-source=<the empty tree> -c core.fsmonitor=false -c core.hooksPath=/dev/null -c diff.ignoreSubmodules=all`. What a session wrote in the tree (`tools/test-gate/features/closed-environment.feature`, rule « the gate enters no repository nested in its tree », `diff.feature`, rule « what a session wrote in the tree hides none of the lines it changed », and the case `nested repository` of `features/sandbox/gate-worktree.feature`): a repository nested in the tree is refused by the reading of the changes (not tracked, recorded by the head, or recorded by the head and gone from the index) and by the verbs of the lease that run or certify a candidate (`exec`, `candidate`, `verify`, `GATE_NESTED_REPOSITORY`; `recover` stays open), and the witness program its configuration names as a filter does not run, though a `.gitmodules` of the tree sets `ignore = none`, while it runs under a `git status` without the options; the delivery (`tools/deliver/features/ports.feature`, rule « git enters no repository nested in the tree », and `sequence.feature`) asks for a nested repository before anything else, stops with « dépôt imbriqué dans l'arbre », and none of `holdsNestedRepository`, `isClean`, `fetch` and `head` starts the witness, which a `.gitmodules` with `fetchRecurseSubmodules = true` makes a plain `git fetch` start; the lease calls dirty a tree whose file holds bytes the commit does not hold while git calls it clean (an `ident` attribute), a mode the commit does not hold, or a link in place of a file (case `rewritten bytes`); a name that is not UTF-8 and a changed path whose patch is empty are refused (`domain.feature`); a changed file keeps its changed lines under a `-diff` or `binary` attribute (tracked, or left out of the commit by an ignore rule), with a NUL byte, with a name git would quote, and when an `ident` attribute makes git call it unchanged. With real git: a repository whose configuration names a witness program as `core.fsmonitor` is read by the gate without the witness running, and the witness runs when git is started on the same repository without the options of the gate, which reads the `core.fsmonitor` of the configuration (`closed-environment.feature`, through `gitWithOptions`); a `pre-push` hook of the worktree is not run by a delivery that pushes, and runs under a `git push` started directly (`tools/deliver/features/git-environment.feature`).
- The names the git of the delivery receives (`tools/deliver/features/git-environment.feature`): a fake git, the program of the adapter, records its environment; for each of the eight methods it received exactly the names of the list of `deliver.json` that the host set and `GIT_TERMINAL_PROMPT`, not `NODE_OPTIONS`, `GIT_DIR` nor `GIT_EXEC_PATH`; a name of the list that the host does not set is not received, one set empty is.
- The set of names of the key `environment` (`tools/deliver/features/config.feature`, `environment-fresh.feature`): the schema accepts a list of 1 or more names, none twice, each in a closed set of ten built in a function; `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `GIT`, `GIT_DIR`, `Z_`, `constructor` and a list of names outside the set are refused, at the position of the name. Only the own properties of the host environment count (`environment-fresh.feature`, a host that sets nothing and the name `constructor`; it fails when `Object.hasOwn` is removed).
- The two lists written twice (`features/arch/closed-git-environment-text.feature`): the list of `tree-fingerprint.ts` and the one of the gate's `git.ts` are read from the text of the two files and are the same; four broken copies (a name changed, removed, added, two swapped) are refused.

## Repository and architecture guard

`features/descriptive/doc-paths.feature`: in `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`, `SECURITY.md` and the documents of `docs/` that describe the tree, every token between backticks, without a space, that holds a slash and whose first segment is an entry of the root names a file or a directory that exists; a pattern, a placeholder or a path into a generated directory is not checked. `features/descriptive/journal.feature`: the journal keeps every section.

`features/repository/repository.feature`: "the repository typechecks" runs `tsc -b` on the root `tsconfig.json`, "the repository is formatted" runs `prettier --check .`; both show the tool output when they fail. Validation of the Claude Code plugin (`claude plugin validate --strict`) needs the Claude Code binary, which CI runners do not have: it belongs to brick 1c.

`features/arch/runtime-entry.feature` starts the shell entry `aos` as a host process, from a copy of the launcher with no `node_modules` nor `dist`, at paths that hold a space, with a spy npm first on the `PATH`: each refusal exits 2 with its one line, never enters npm, writes nothing under the root and leaves an existing report as it was, in the order of `tools/runtime/src/domain/refusal.ts` (the grammar, a program that begins with `-` included, then the setting, then the Node of a trusted location, then the admission); an admitted launch keeps the directory, the arguments, stdin and the status of the program, which sees exactly the locations of one new run and no inherited `NODE_OPTIONS` nor coverage output; it also reads the import specifiers of `tools/runtime/src` (Node's built-ins other than a process launcher, and the tool's own modules, nothing else). A child process kills no mutant: the decisions are judged in process by `tools/runtime/features`.

`features/arch` also holds three literal checks of the text of files: `closed-git-environment-text.feature` (the three production files that start git, see « The closed environment of git » above), `no-container-command.feature` (the strings `docker` and `colima`, in any case, appear in no file the rule reads outside a closed list of six, each entry with its reason, and each entry is in the tree and still holds one; the rule reads the regular files, and the symbolic links by their target, that git tracks or would track, leaving out Markdown, the files under a `results` directory and the records of `steps/`, while every `step.json` is read; the scenarios require the whole file to equal what the function produces, the message naming the command that regenerates (`./aos -- npm run diagram:isolation`, after a build), and show on the produced image that every text carries a size and the monospace family the measure assumes, and that each kind is drawn at its measured size; the poisoned copies are each refused for their own reason: a profile that gains a write path with the file unchanged, the file edited by hand, an item one character longer than the longest item, the sentence of the denied reads too long for its line, a constant of the image too long for its room, a `font-family` or a `font-size` set on a `tspan` of a copy of the produced markup with one added. That the function starts no process, and the factor of the measure and the families it was measured for, are read by the reviewer, not shown by a scenario. `docs/diagrams/architecture.svg` is drawn by hand: it shows who starts what and what holds the credential, and the reviewer reads it like the README; the lists of each profile are in the generated image. ## Checklist for a new brick

1. Unit scenarios in `<component>/features/` for each layer it touches.
2. A `Scenario Outline` contract for each new port, one `Examples` row per adapter.
3. An end-to-end scenario in `features/integration/` if it is on the path of a call, including a failure with a named `error.code`.
4. A guard rule and a fixture row in `features/arch/guard.feature` if it adds a boundary.
5. A load-and-schema scenario with a broken copy for each descriptive file.
6. 0 surviving mutant on the changed production lines.
7. `./aos -- npm run check` green.

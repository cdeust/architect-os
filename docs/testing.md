# Testing

Every test is a Gherkin scenario run by `@cucumber/cucumber` (`npm test` is `cucumber-js`, after `tsc -b`: the platform launches its modules and workers from their built entry points). Typecheck, format and the architecture guard are scenarios too, so `npm run check` is `npm test`. No test calls the network or Anthropic. The CI gate (`npm run gate`, `docs/design/platform-v3-srt.md` §7) adds the pickle count and mutation testing on top.

## Three families

| Family     | Where                                                                                 | What it proves                                                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| End to end | `features/<area>/*.feature`, steps in `features/steps`, support in `features/support` | Cross-cutting behaviour with the real thing: real srt sandboxes (`features/sandbox`), real Postgres (`@postgres`), the guard, the repository, descriptive files.                 |
| Unit       | `<component>/features/*.feature`, steps in `<component>/features/steps`               | One layer in isolation, ports replaced by in-memory adapters or small fakes; port contracts as `Scenario Outline`s.                                                              |
| Mutation   | Stryker, run by `npm run gate` on the production lines the diff changed               | The scenarios kill every mutant of a changed line. A surviving mutant fails the gate; an equivalent is marked `// Stryker disable next-line <Mutator>: équivalent: <invariant>`. |

Components: `packages/contracts`, `packages/sandbox`, `data`, `gateway`, `services/memory`, `modules/broker`, `modules/memory`, `tools/test-gate`, `tools/evidence`, `tools/watch`, `tools/deliver` (its `tools/deliver/features/ports.feature` holds the contract of each port of the command, one row per adapter; its `tools/deliver/features/sequence.feature` runs the six phases over the in-memory doubles). Areas of root `features/`: `integration`, `arch`, `descriptive`, `infra`, `repository`, `sandbox`. `features/sandbox/` holds only scenarios that start real srt sandboxes (Linux and macOS); where srt cannot run, they fail, never skip. `features/sandbox/escape.feature`, the exit of brick 1b, runs eight attacks (home secret, write outside, git hook, example.com, 169.254.169.254, Postgres socket, another task's folder, `unshare -r`) inside each profile, builder, reviewer, module and worker, and observes on the host that each fails; a witness outline runs the five local ones on the host without srt and sees them succeed. Its network attacks start inside the sandbox only, where they must be refused. `features/sandbox/recall.feature` and `features/sandbox/remember.feature` prove `memory.recall` and `memory.remember` through the committed topology under real srt (module and worker in their profiles, the broker before a fake model); `remember` is proven in data, the store holds the memory and its id is the `memory_id` of the answer.

## Rules of the suite

- One `cucumber.mjs`: `paths` over both layouts, `retry: 0`, `strict: true`, no `tags`, no `name`. A skipped, pending or undefined step is a failure.
- No computed `Examples` table: every row is literal in the `.feature`.
- Step text is unique across the repository (all steps load in one run; an ambiguous step fails).
- Steps are strict TypeScript using `node:assert/strict`, typechecked by `npm run typecheck`.
- No scenario is conditional on the host. A scenario that needs Postgres or srt and cannot get it fails.

## Running

```bash
npm test                              # every scenario (cucumber-js); also `npm run check`
npx cucumber-js <path>.feature        # adds to the configured paths, see below
npm run gate                          # plan, cucumber, Stryker on the perimeter, verdict
npm run gate -- --job macos           # features/sandbox only
```

One set of scenarios is outside the gate, with its own profile in `cucumber.mjs`: `modules/broker/live/` spends on the real API with a real key, and is a command of the owner. It is not counted by the gate, and mutation does not apply to it: it adds no production line of its own.

Positional paths given to `cucumber-js` are merged with the `paths` of `cucumber.mjs`; they add to the run instead of narrowing it. To run one feature, use a profile or a throwaway config naming only that path (`npx cucumber-js --config <file>`). The `macos` profile of `cucumber.mjs` runs `features/sandbox` alone.

## `@postgres`: a disposable database

Scenarios tagged `@postgres` (the `postgres` rows of the data-store contract) get a real database from the hook in `features/support/postgres.ts`: the first one starts a disposable Postgres 17 with pgvector, from `PG_BIN` or the `pg_ctl` found on `PATH`, listening on a Unix socket only (no TCP), and each scenario gets a fresh database. Without a PostgreSQL the scenario fails; it is never skipped. A detached watchdog (`features/support/pg-watchdog.mjs`) stops the server and removes its directory when the test process is gone, however it died (Stryker kills its workers, so `AfterAll` may never run, and an orphan server keeps a SysV shared memory segment; macOS allows 32); `features/infra/postgres-watchdog.feature` proves it with a SIGKILL.

## End to end

Nothing here is composed for a test where the production code can compose it:

- `features/sandbox/gateway-entry.feature`: the process is `node gateway/dist/src/serve.js`, given only its configuration. It starts `data` and the broker as its children, the module and the worker under a real srt, and serves a real MCP client over HTTP, before a fake model over HTTPS.
- `features/sandbox/gateway-native.feature`, `features/sandbox/recall.feature`, `features/sandbox/remember.feature`: the platform composed by the production code, under a real srt.
- `features/integration/gateway.feature`, `features/integration/agent-worker.feature`, `features/integration/usage.feature`: the same paths in one process over streams, the sandboxes replaced by in-memory runners; the worker runs the real Claude Code binary against a fake model on the loopback.

No scenario calls the real API: `modules/broker/live/` is the owner's command for that, outside the gate.

## Port contracts

A contract is one `Scenario Outline` per case with one `Examples` row per adapter. Adding an adapter means adding one row to each outline. Example: `data/features/data-store-contract.feature` runs the same six cases on `in-memory` and on `postgres`. The `Examples` of `features/descriptive/claude-files.feature` list the committed `.claude/agents` and `.claude/commands` files: a new file adds its row.

## Repository and architecture guard

`features/descriptive/doc-paths.feature`: every path that `CLAUDE.md`, `CONTRIBUTING.md`, `README.md` and the documents of `docs/` that describe the tree cite between backticks exists; a pattern, a placeholder or a path into a generated directory is not checked. `features/descriptive/journal.feature`: the journal keeps every section.

`features/repository/repository.feature`: "the repository typechecks" runs `tsc -b` on the root `tsconfig.json`, "the repository is formatted" runs `prettier --check .`; both show the tool output when they fail. Validation of the Claude Code plugin (`claude plugin validate --strict`) needs the Claude Code binary, which CI runners do not have: it belongs to brick 1c.

`.dependency-cruiser.cjs` holds the rules (layers, no cross-component import, `pg` / agent SDK / MCP SDK / `child_process` / srt confinement, no cycles). `features/arch/guard.feature` writes one temporary violating file per rule under the real component directories, runs the guard, asserts each rule fires on its file, deletes the files and asserts the tree is green again. To see it by hand:

```bash
echo "import 'pg';" > gateway/src/application/zz-tmp.ts && npm run arch   # red
rm gateway/src/application/zz-tmp.ts && npm run arch                      # green
```

## Known gaps

- The agent runs with the real Claude Code binary against a fake model (`features/integration/agent-worker.feature`). It is not exercised against the real API in the gate (it needs a key); `modules/broker/live/` is the owner's command for that.

## Checklist for a new brick

1. Unit scenarios in `<component>/features/` for each layer it touches.
2. A `Scenario Outline` contract for each new port, one `Examples` row per adapter.
3. An end-to-end scenario in `features/integration/` if it is on the path of a call, including a failure with a named `error.code`.
4. A guard rule and a fixture row in `features/arch/guard.feature` if it adds a boundary.
5. A load-and-schema scenario with a broken copy for each descriptive file.
6. 0 surviving mutant on the changed production lines.
7. `npm run check` green.

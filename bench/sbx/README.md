# Builder qualification in Docker Sandboxes

These operator-run probes exercise the pinned Linux ARM64 clients in Docker Sandboxes 0.54.0. They cover offline client behavior and the ChatGPT subscription path in the builder qualification design. The first nine trials below used a text-only host implementation. Production Step now runs Claude under SRT and Codex under SBX. The [production scenarios](native-builder.feature) exercise native tool calls through the host proxy with an offline provider. [Builder qualification design](../../docs/design/orchestration-fable-5-2.md)

Start the commands through the repository launcher, with the two release archives on the development volume. The Codex input is the npm tarball for `@openai/codex@0.170.0-linux-arm64`. The [Antigravity probe](antigravity.md) records Google's original release URL and checksum. The host selects the installed shell template and its agent kit by separate immutable references from `isolation.json`. Before staging the client it checks the actual VM image digest and installed kit against those references. Both probes verify the archive and Linux executable.

```sh
./aos -- node --test bench/sbx/*.test.mjs
./aos -- python3 -B -m unittest discover -s bench/sbx
./aos -- node bench/sbx/text-turn.mjs "$CODEX_LINUX_ARM64_TGZ"
./aos -- node bench/sbx/text-turn.mjs "$CODEX_LINUX_ARM64_TGZ" --moderation-fixture
./aos -- node bench/sbx/codex.mjs "$CODEX_LINUX_ARM64_TGZ"
./aos -- node bench/sbx/agy.mjs "$AGY_LINUX_ARM64_TGZ" 180000
```

The host creates one synthetic workspace under the admitted run. Before either client starts, it checks the host mounts, runtime mounts, published ports, static MCP server set and effective network policy. An active sandbox-scoped wildcard denial must cover TCP and UDP, with zero allow rules. The policy engine must explicitly refuse a destination for each protocol. The host checks that the unprivileged client cannot write the guest daemon socket before staging either client. The guest receives the pinned probe assets and runs the client under UID 65534. The host removes the named VM and verifies its absence before deleting the temporary workspace.

For Codex the host keeps its original witness file open for the whole run. After confirming VM removal it checks the file identity and reads at most 21 bytes from that descriptor for the expected 20-byte marker. On SIGINT, SIGTERM or SIGHUP the host cancels the current exchange and waits for shutdown. A failed stop or inconclusive VM creation retains the workspace and reports its path and VM name for recovery. The original probe failure remains available alongside a cleanup failure.

## Where the account credential lives

Docker's `sbx` CLI creates and inspects the VM. The bench creates it with `--deny-network '**'`, `--static-mcp none` and `--pull never`, then verifies the resulting policy and mounts. [Docker SBX CLI](https://docs.docker.com/reference/cli/sbx/) · [Sandbox creation options](https://docs.docker.com/reference/cli/sbx/create/)

Docker also offers `sbx secret set openai --oauth`. Its local OpenAI OAuth flow stores the credential at global scope. Docker documents the system Keychain as its credential store on macOS. [Docker OAuth command](https://docs.docker.com/reference/cli/sbx/secret/set/) · [Docker credential storage](https://docs.docker.com/ai/sandboxes/configuration/credentials/)

The operator obtains Sign in with ChatGPT (SIWC) consent for Architect OS. One host process keeps the access and rotating refresh tokens in memory across VM launches. The host serializes refreshes for that account and validates the replacement before use. Each run gets its own catalog-only or single-text-request capability. The VM receives challenges and validated results over process pipes. The host process ends with the bench, and the account tokens are never written to disk or passed into a VM. [SIWC session renewal](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions#refreshing-tokens) · [`accountSessionTransport`](subscription-account.mjs) · [`openSubscriptionSession`](subscription-session.mjs)

For the account-bound command probe, the host checks the account catalog and supplies a fresh challenge to the pinned Codex app-server. Through `command/exec` it runs `sha256sum challenge` in the guest. The host reconstructs the digest independently and verifies the empty shared workspace after shutdown. This operation uses zero model requests. [`runAccountExec`](account-exec.mjs)

## A single text turn through the host

When the host withholds a response, it can send a one-field denial over the same pipe. The guest serves a fixed HTTP 403 with an empty body to Codex. The host verifies the pinned client's exit code 1, a failed native turn without message output, the original challenge digest and an empty workspace after VM removal. An interrupted exchange has no such receipt. Provider metering, when available, stays in the host observation.

The native Codex client runs with a fresh home and a read-only sandbox. Its loopback server uses the existing SBX process pipes. The host sends the prompt, receives the native request, sends the answer and receives the final receipt. The native request releases a single challenge chosen by the host. The host validates the model, the complete answer and the token counts before sending a new text-only event stream to the guest. After Codex exits, the host compares the native receipt with its own observation, stops the VM and checks the shared workspace is empty.

The CLI command above uses a synthetic response. Its receipt identifies the fixture, zero upstream requests, and synthetic token counts. The host entry point `runHostedTurn(archive, requestText)` accepts a model response from a separately controlled host broker. That broker owns consent, subscription eligibility, the upstream destination, and evidence of the actual request and its billing. The bench has no token parameter. The host verifies the exchange against the native receipt after the VM has shut down. The fixture uses no account and costs zero dollars.

For a native text turn, the host's single-use capability calls `requestNativeSubscriptionText` with the private receipt and HTTPS transport. The request constructor accepts the host's UUID challenge and sends an input array, an empty tool list, `store: false` and `stream: true`. SIWC lists `max_output_tokens` as unsupported. The host checks the accepted answer locally after generation. Its receipt records the dispatch time and a randomly generated client request ID for billing support. [Native subscription exchange](subscription-exchange.mjs) · [SIWC preview limits](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) · [OpenAI request IDs](https://developers.openai.com/api/reference/overview#supplying-your-own-request-id-with-x-client-request-id)

HTTP 200 establishes that the endpoint answered. The server-sent event (SSE) stream carries the provider's terminal status and usage. The host observer can record a completed, failed or incomplete terminal linked to the response ID and model from `response.created`. It records input, output and total tokens when the counts are valid and agree. The native decoder separately decides whether it can release the answer. A conflicting routing state or a policy notification can still stop the guest even when the host has observed a metered terminal. Dollar cost requires separate billing evidence. [Subscription inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) · [Responses streaming events](https://developers.openai.com/api/reference/resources/responses/streaming-events)

The offline positive probe runs the pinned Codex client in SBX. The host serves a response-bound inline presentation notice and the reasoning-inclusion HTTP flag, checks the fresh model catalogue through a fixture, then verifies the answer and usage against the native receipt. The negative probe injects an active safety block in the same transport. The host records eight input and four output fixture tokens and withholds the text. Both probes remove their VM. The private account operator also checks the digest of the host-generated challenge after the worker exits. [Native notifications](https://github.com/openai/codex/blob/29eb79e9866b3262a777fdf8195c1b9e63684c91/codex-rs/codex-api/src/sse/responses.rs#L216-L297)

For the buffering headers seen on trial 5, the pinned client applies their parameters when a buffering event arrives. For the catalogue notification seen on trial 6, the host requires a fresh visible match for the requested model before releasing an otherwise valid reply. This check uses the same account and the fixed catalogue endpoint. It separately binds a supported final-answer display decision to a specific message when supplied. The receipt contains no actionable clearance for this report. Raw report values stay on the host. The production blocker is a verified way to resolve this notification before passing text to a delegated client.
